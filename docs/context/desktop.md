# Desktop app (Windows and Linux)

The Tauri v2 project in `app/` (its own Cargo workspace; ADR-0006) shows the hub's web UI in a window, with a tray, a mini player and media keys. On first run the listener picks **This computer is my hub** (the app runs the hub in-process with a bundled slskd) or **Connect to a hub** (pair with one elsewhere). Every player action runs in the web UI. Design spec: `design/desktop/DESKTOP.md`. Decisions: [ADR-0006](../adr/0006-one-tauri-app-for-windows-linux-android.md), [ADR-0060](../adr/0060-desktop-wrapper-pages-token-ipc.md). Android: [android.md](android.md).

## Run it

- **Every dev build gets its own identifier.** This is the default way to build or run `app/`:
  `cd app && TAURI_CONFIG='{"identifier":"io.github.tannhausercommons.lull.dev"}' cargo run` (PowerShell: `$env:TAURI_CONFIG='{"identifier":"io.github.tannhausercommons.lull.dev"}'` first). Set `CARGO_TARGET_DIR` outside `Desktop` on Windows. The first build downloads slskd (55 MB), yt-dlp (24 MB on Windows, 41 MB on Linux) and Deno (a 43 MB zip) into `app/binaries/`.
  - **Why:** without `TAURI_CONFIG` a dev build *is* the installed app as far as the OS can tell: same identifier, so the same settings (device token included), WebView2 profile and single-instance lock. Beside an installed lull it hands over to it and exits, and anything written into "its" settings is the installed app's.
  - Use one test identifier per purpose (`….lull.dev`, `….lull.<what you test>`); seed, inspect and delete only that identifier's folders (the list below, with its name), never `io.github.tannhausercommons.lull`'s.
  - Only `npm run bundle` and CI's release builds use the real identifier.
- Pages in `web/desktop/` and the staged web files are embedded at compile time: rebuild after editing them. The web UI itself comes from the hub; the in-process hub embeds it at compile time too (release builds), so web edits need a rebuild here.
- **Inspecting the webviews:** start with `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333` and open `http://127.0.0.1:9333/json`; each window is a DevTools target.
  - **Out of sight means hidden:** `node tests/desktop/visibility.mjs [port]` checks, against a running debug build signed in to a hub, that main's page reports hidden while the mini player hides main and while main is minimised, visible again once it is back, and that a song goes on playing out of sight (`platform::set_webview_awake`). It reads the page over a bare DevTools socket: Playwright attached over CDP holds a page "visible", so measure visibility without it.
- **Where things live** (Windows; Linux uses `~/.config/` and `~/.local/share/` with the same identifier). These are the installed app's; a dev build's are the same paths under its own identifier:
  - `%APPDATA%\io.github.tannhausercommons.lull\settings.json`: the app's settings, including its device token;
  - `%APPDATA%\io.github.tannhausercommons.lull\hub\`: the hub's database (`LULL_DATA_DIR`);
  - `%APPDATA%\io.github.tannhausercommons.lull\slskd\`: slskd's app dir (its data, logs and `slskd.yml`);
  - `%APPDATA%\io.github.tannhausercommons.lull\transfers\`: `complete/` and `incomplete/` (`LULL_TRANSFERS_DIR`);
  - `%LOCALAPPDATA%\io.github.tannhausercommons.lull\logs\hub.log`: the hub's log, truncated at each start;
  - `%LOCALAPPDATA%\io.github.tannhausercommons.lull\logs\webview.log` (and `webview.log.1`): which WebView2 runs, and every crash of a window's page (Crashes, below);
  - `%LOCALAPPDATA%\io.github.tannhausercommons.lull\EBWebView\Crashpad\reports\*.dmp`: WebView2's crash dumps, kept here and never sent to Microsoft;
  - `%LOCALAPPDATA%\io.github.tannhausercommons.lull\logs\lull.dmp`: a minidump of lull's own process if it crashes, overwritten by the next one;
  - `%LOCALAPPDATA%\io.github.tannhausercommons.lull\EBWebView`: WebView2 data.
- Bundles: `npm ci && npm run bundle` in `app/`. CI does this (`.github/workflows/app.yml`): it compiles lull's own Last.fm key into the hub (secrets `LULL_LASTFM_API_KEY`/`_SECRET`, as the image does); a `v*` tag sets the version from the tag, signs the updater files (secret `TAURI_SIGNING_PRIVATE_KEY`, no password; the .deb and .rpm with `tauri signer sign`, since the bundler signs only the installer and the AppImage) and attaches the Windows installers, the Linux deb, rpm and AppImage packages, their `.sig` files, the Android APK and `latest.json` (api.md, App releases) to that tag's Release; a run by hand, on any branch, runs the app's checks and keeps unsigned bundles as workflow artifacts. Four desktop builds, each native on GitHub's runner for its architecture: Windows x64 (`windows-latest`) and ARM64 (`windows-11-arm`), Linux x64 (`ubuntu-22.04`) and ARM64 (`ubuntu-22.04-arm`), the oldest glibc of each.
- **The AUR** (`lull-bin`, ADR-0063): Arch listeners get the release's .deb on Arch's own WebKitGTK and libraries, as most Tauri apps there do. `scripts/aur-pkgbuild.sh` writes the PKGBUILD from `packaging/aur/PKGBUILD.in`: the version, the sha256 of each architecture's .deb and its `.sig`, the release key (from `tauri.conf.json`'s updater key), and Arch's packages it needs. The PKGBUILD checks the .deb's minisign signature in `prepare()`, puts lull and its slskd, yt-dlp and Deno in `/usr/lib/lull/` (Arch has its own yt-dlp and deno; lull finds its own next to itself) with `/usr/bin/lull` pointing there, and writes `/usr/lib/lull/updates-from`: lull's own updater then stands down (`Status::Packaged`, "Updates come with the AUR (lull-bin)" in Settings and the tray), since pacman owns those files.
  - **CI** (`.github/workflows/aur.yml`): in Arch's own container, `makepkg` builds it against a published release (checksums and the signature checked), `namcap` checks it, pacman installs it, and lull starts under Xvfb until its window draws; the aarch64 sources are downloaded and checked too (no Arch aarch64 runner to start it on). The queue runs it when `packaging/aur/` or the script change, against the newest release; a release's run (`app.yml`'s `aur` job, after the Release is up) then pushes the PKGBUILD and `.SRCINFO` to `ssh://aur@aur.archlinux.org/lull-bin.git`, checking the AUR's published host key.
  - **The secret:** the push needs `AUR_SSH_KEY`, the private half of an SSH key the AUR account has, from Bitwarden's `lull/AUR_SSH_KEY`. Until it is set the job says so and stops there.
- **Cutting a release:** `mise run release 0.2.0` on an up-to-date, clean `main` (`scripts/release.sh`) sets the version in `Cargo.toml` (the hub's workspace) and `app/Cargo.toml` and Android's versionCode, updates both lock files, drafts the F-Droid changelog (android.md, Build it), commits `build(release): lull 0.2.0` and tags `v0.2.0`. Nothing is pushed: run `mise run check`, then `git push origin main v0.2.0` publishes it. The tag's run builds for about half an hour; the Release appears when every bundle is in.

## Launch

1. **No hub chosen:** `main` opens the welcome page: **This computer is my hub** or **Connect to a hub**.
2. **This computer:** `local_hub::start` (off the main thread), then `main` loads `http://127.0.0.1:8484` with the device cookie. A failure loads the hub-error page with the reason ("Port 8484 is already used…"); **Try again** starts it again, **Use another hub** goes back to the welcome page.
3. **A hub elsewhere:** Rust probes `GET /health` (10 s), then `GET /api/ping` with the token. Both fine: `main` loads the hub's origin with the device cookie. Unpaired (401): the connect page, saying so. No answer: the unreachable page with the error, and the app keeps trying by itself (`app/src/reconnect.rs`, the desktop's and Android's):
   - **When:** after 2, 4, 8 and 16 s, then every 30 s; at once on **Retry now** (`window_action {retry}` wakes it); and at once when the network changes (Windows: this computer's IPv4 addresses change, `NotifyAddrChange`, as when Tailscale comes up; it waits 1.5 s for names to resolve). Linux follows the backoff alone.
   - **Each probe** has a hard limit of 25 s, whatever it waits on (a name lookup, a connection, TLS); one that runs out counts as failed. So does the first, at launch.
   - **Whatever the window does:** it runs in Rust, hidden, minimised or in the tray alike. Every outcome reaches the page as `reconnect`, and the page only shows it (its countdown is display). It stops when `main` shows anything else.
   - **Why:** v0.2.1 retried from the page's own timer, and Rust answered a failed retry by loading the same page again: same address, same error, same URL, which a webview doesn't load again, so the page sat on "trying now" with Attempt 1 for good (a hub name that didn't resolve when the app started, before Tailscale's DNS was up). Every bundled page `main` goes to is numbered now (`pages::fresh`), so going to the page it shows loads it again.
4. `main` shows once its page has loaded, unless **Start in the tray** is on and a tray exists, or **Keep lull running when closed** is on and lull started at login. It starts at `about:blank` when the cookie has to go in first; that page never shows.
5. The app switches between its pages by changing the page's hash, so `desktop.js` re-renders on `hashchange`.

**Pairing** (connect page): the page lists hubs found by mDNS for 3 s (**Search again**), each with its most reachable IPv4 address (home LAN ranges first, Tailscale's 100.64/10 next, link-local last), or takes an address (`192.168.1.20:8484` means http, a dotted name like `hub.example.ts.net` means https). With a 6-character pair code from a paired device, `find_hub` checks the address, then `window_action {pair}` posts `/api/pair { code, name: "lull on <computer>", kind: app }` and keeps the token. Choosing a remote hub while this computer's hub runs restarts the app, because the hub can't stop under its open connections.

**The device token** (ADR-0002): the app keeps one token for the hub it uses, in `settings.json`. At each launch it goes into the webview as the session cookie `lull_device` for the hub's host (HttpOnly, SameSite Lax, Secure on https). Rust sends it as `Authorization: Bearer`. Changing the hub forgets it.

## This computer is the hub

`local_hub::start`:
1. **Paths** under the app's data dir (above). The hub's log goes to `hub.log` through `tracing`.
2. **Env** for `lull_server::run_with` (shown as locked in Settings, ADR-0002): `LULL_DATA_DIR`, `LULL_LISTEN=0.0.0.0:8484` (phones reach it on the LAN; Windows asks to allow it through the firewall on first run), `LULL_SLSKD_URL` (loopback, a free port chosen per run), `LULL_SLSKD_API_KEY` (random per run), `LULL_TRANSFERS_DIR`, `LULL_SLSKD_CONFIG_FILE`, and `LULL_YTDLP`/`LULL_DENO` (the sidecars next to `lull.exe`; when one is missing the hub looks on PATH).
3. **First run seeds** `LULL_MUSIC_DIR` with the OS Music folder as a *stored* setting, so the hub's setup screen can change it.
   **Each start stores** `LULL_PUBLIC_URL` = `http://<LAN address>:8484` (the address of the default route), because pair codes carry it and the webview itself talks to `127.0.0.1`. It does so only while the stored value is empty or plain http; an https address (Tailscale serve, or the listener's own) is never touched.
4. **The app's own device:** the stored token if `devices::verify` still knows it, else `devices::create(name, Kind::App)`.
5. **slskd starts**, then the hub; the app waits until port 8484 accepts connections (30 s at most) or the hub's task fails.
6. **mDNS** advertises `_lull._tcp` with the computer's name and port 8484. A network that refuses multicast only loses discovery.
7. **Following settings:** after each restart of its crates the hub hands slskd the new settings (`run_with`), and slskd restarts if what it shares changed (`LULL_MUSIC_DIR`, `LULL_SHARE`): slskd takes shares only at start.

**yt-dlp and Deno** (YouTube, docs/context/youtube.md), the versions the server image pins: fetched by `build.rs` like slskd (yt-dlp's standalone `yt-dlp.exe`, `yt-dlp_arm64.exe`, `yt-dlp_linux` or `yt-dlp_linux_aarch64`; Deno's release zip for the target), checked against pinned sha256s and shipped as sidecars (`binaries/yt-dlp-<target>`, `binaries/deno-<target>`). The hub runs them itself, without a console window; Keep yt-dlp up to date may put a newer yt-dlp in the hub's data folder. To bump either, change the version and hashes in `build.rs` and the `Dockerfile` together.

**slskd** (`crates/server/src/managed/slskd.rs`, shared with the Linux package), 0.26.2 like the deploy kit:
- **Fetched at build time** by `build.rs`: the zip for the target (win-x64, win-arm64, linux-x64, linux-arm64: each architecture runs its own build, none under emulation), from the URL pinned with its sha256, kept in `app/binaries/`; the binary becomes `binaries/slskd-<target-triple>[.exe]`, Tauri's sidecar name, and ships next to `lull.exe`, with `slskd-LICENSE.txt` and `licenses/THIRD-PARTY.md`.
- **Linux gets slskd's own release.** Windows gets lull's build of it (ADR-0062, `app/slskd/`): one line changed so lull can read a song while slskd downloads it, which stock slskd forbids on Windows ("os error 32"). CI builds it from slskd's tag, twice, to the same bytes, and they must be the pinned ones (`slskd-windows` workflow, inside `slskd-contract`); `slskd-windows-publish`, dispatched by hand on main, attaches the zips to the `slskd-<build>` pre-release that `build.rs` downloads.
- **To bump it:** Linux's URLs and hashes from `gh release view <v> --repo slskd/slskd --json assets`; for Windows, a new lull build (ADR-0062, Consequences). The contract (`tests/slskd-contract/`) must pass with `--native` on Windows and in Docker on Linux.
- **Command line** (fixed for the run): `--app-dir`, `--http-ip-address 127.0.0.1`, `--http-port`, `--no-https`, `--headless` (lull is the UI; `--content-path` points at the app dir because slskd checks that its static folder exists even then), `--downloads <transfers>/complete`, `--incomplete <transfers>/incomplete`, and `--shared <music dir>` unless `LULL_SHARE=none`.
- **Env** (not in the process list): `SLSKD_API_KEY`, and slskd's own web login (`lull` and a random password, never the default).
- **No console window:** like every program lull starts (yt-dlp, which starts Deno in its windowless console, and Tailscale), slskd is started through `lull_core::process::command`, which sets Windows' `CREATE_NO_WINDOW`. Without it, a release build (no console of its own) opened a console window for slskd, and closing that window stopped slskd, which the supervisor then started again. Clippy refuses `Command::new` anywhere else (`clippy.toml`). A dev build has a console, so it never showed one; `process::tests` starts a program from a process without a console to check it.
- **`slskd.yml`** in its app dir (created empty before slskd's first start, so its watcher follows it) belongs to the hub: the app passes it as `LULL_SLSKD_CONFIG_FILE`, and the soulseek crate writes the account from `LULL_SOULSEEK_USERNAME`/`PASSWORD` into it and logs slskd in again (docs/context/soulseek.md). slskd reads env < yml < command line and reloads the file by itself.
- **One supervisor thread** owns the process and does every spawn. slskd never outlives the app (`local_hub.rs`, its `Tie`): on Windows it sits in a kill-on-close job object, on Linux it gets `PR_SET_PDEATHSIG` (tied to the spawning thread, hence the one thread). Quitting stops it; so does an update.
- **Restarts:** slskd that stops by itself starts again after 5 s, then 10, 20 and so on up to 5 minutes while it keeps stopping; after 10 minutes of running the wait starts over at 5 s. A failed start is retried the same way. When the hub finds slskd wedged and fresh logins didn't help, `/health` says `services.soulseek.extra.restartSlskd` (docs/context/soulseek.md). Headless slskd refuses the web login the hub would restart it with, so the hub checks that every minute and restarts the process, at most once per 30 minutes. Same port and API key each time, so the hub keeps its URL.
- **Licence:** AGPL-3.0, unmodified. `licenses/THIRD-PARTY.md` and slskd's `LICENSE` ship next to the app.

**Tailscale** (`crates/server/src/managed/tailscale.rs`): when this computer is the hub, Settings > App can show `LullDesktop.tailscale()`: `{ installed, running, url, serving }` from `tailscale status --json` and `tailscale serve status --json` (read-only). The listener's click on **Use Tailscale** calls `LullDesktop.tailscaleServe()`, which runs `tailscale serve --bg 8484` (20 s at most: it waits when HTTPS is off in the tailnet) and then stores the https address as `LULL_PUBLIC_URL` through `PATCH /api/config`, so pair codes carry it.

**Updates** (`updater.rs`): the app reads `latest.json` from the newest GitHub Release (`plugins.updater.endpoints`) at launch, every 6 hours while it runs, and when the listener asks. Background checks are silent: they only change Settings and the tray. A newer build downloads in the background and its signature is checked against `plugins.updater.pubkey`; nothing installs before the listener's **Restart to update**. Windows runs the NSIS installer passively and restarts lull; Linux replaces the AppImage, or installs the .deb or .rpm the app came from (after the system's password prompt), and restarts. GitHub gets 30 s to connect and to send each part of an answer.
- **States** (`updates::Status`, the same in Settings > App and the tray's update item above **Quit lull**): not checked yet (**Check for updates**); checking; up to date (**lull 0.1.0 is up to date**, a click checks again); downloading, with its percentage; ready (**Restart to update to lull X**); failed, in plain words where the cause is plain ("Couldn't reach GitHub. Are you offline?", "No lull release has been published yet"), else the updater's own message.
- A check while one runs, while an update downloads or while one waits returns the current state instead of starting another.

## Crashes

When a process behind a window's page dies, `recovery.rs` hears it (WebView2's `ProcessFailed` on Windows, WebKitGTK's `web-process-terminated` on Linux), writes one line to `logs/webview.log` and brings the window back, so the engine's own "This page is having a problem" never stays up.
- **lull's own process** crashing (not a page's) writes `logs\lull.dmp` (an unhandled-exception filter calling dbghelp's `MiniDumpWriteDump`, with the path made at start), then Windows ends it as usual.
- **One WebView2 environment** for every window (`recovery::builder`), made on the UI thread before the first: wry's own options plus `IsCustomCrashReportingEnabled`, so dumps stay in `EBWebView\Crashpad\reports` on this computer. The log's first line each run names the WebView2 version and that folder.
- **The log line:** the window, the process (renderer, unresponsive renderer, browser, GPU, a helper), the reason, the exit code (`0xC0000005` is an access violation), WebView2's process description and the module it crashed in, then what the app was doing (Classic open, `main` asleep, the mini player, the song and second) and what recovery did. At 256 KB it moves to `webview.log.1`.
- **A renderer hung:** WebView2 says so when the page ignores input for a while (`RENDER_PROCESS_UNRESPONSIVE`). A reload can't run in a busy renderer (tried: the page stayed frozen), so recovery ends that process: the one hosting the window's main frame (`GetProcessExtendedInfos`, matched on the webview's `FrameId`). Its exit then goes on as below, counted once.
- **A renderer exited:** the window reloads. `main` then resumes the song, second and play state it last reported (`resume_after_crash`, once; not while Classic mode plays, since Webamp plays then). The Classic window takes its handoff again, kept current as Webamp reports and moved on by the time since, so Webamp starts where it was. The mini player asks `main` for the player again.
- **A loop** (one window's page dying 3 times in 2 minutes): `main` shows lull's own page (`crashed`) with **Reload**, which loads the web UI again with the same resume; Classic mode hands the queue back to `main` as Webamp would have; the mini player closes.
- **The browser process** (every window's) exited: lull restarts, at most once in 10 minutes (a stamp beside the log).
- **GPU and helper processes:** they come back by themselves; logged only.
- **If it happens** (the listener's steps): open `%LOCALAPPDATA%\io.github.tannhausercommons.lull` in Explorer (Win+R, paste it, Enter). Zip `logs\webview.log` (and `webview.log.1` if it's there), `logs\lull.dmp` if it's there, and the newest `.dmp` in `EBWebView\Crashpad\reports`, and send the zip with the time it happened and what lull was doing. A dump is a few MB and holds the page's memory at the crash: share it only with lull's maintainers. On Linux the log is in `~/.local/share/io.github.tannhausercommons.lull/logs/`; WebKitGTK keeps no dumps.

Verified in a debug build, crashing pages through DevTools (`Page.crash`, `Browser.crashGpuProcess`): `main` while playing (reloaded and played on from the same second), three in a row (lull's page, then Reload), the mini player, the GPU process (logged with `0xC0000005`, nothing else needed), the Classic window once (Webamp started again on the same song) and three times (the queue back in `main`, playing), and `main` while Classic played (it took the queue back when Webamp closed). Opening and closing Classic mode and the mini player 15 times with a song playing crashed nothing. A page hung in a loop and clicked (WebView2 reported it unresponsive after about 10 s) came back playing three times out of three, the third as lull's page (a loop). A 40-minute soak (songs of 20 s, MP3 and FLAC, Discord on) kept lull's own process flat (about 570 to 730 handles, 30 GDI and 44 USER objects, 95 MB), so nothing native grows per song or per event; `main`'s renderer went up and down between about 150 and 580 MB, collected about every 10 minutes.

## The seam with the web UI

The web UI never calls Tauri directly. It uses `window.LullDesktop` from `desktop.js`, and `desktop.js` uses these parts of the web UI's `App`:
- `App.player`: `current`, `currentId`, `state` (`playing`, `pos`, `buffered`, `received`, `durationKnown`, `shuffle`, `repeat`, `volume`, `muted`), `duration`, `toggle`, `next`, `prev`, `pause`, `setShuffle`, `cycleRepeat`, `setVolume`, `seekFraction`;
- `App.isLiked`, `App.toggleLike`, `App.isSaved`, `App.saves.start`, `App.go`, `App.design`, `App.prefs`, `App.banner.list` (the `sys-unreachable` banner means "not connected");
- events `player`, `tick`, `like`, `save`, `ready`, `design`, `prefs`, `route`;
- cover art: the largest `navigator.mediaSession.metadata.artwork`, fetched by the web UI and passed on as a data URL.

**What the web UI calls (`LullDesktop`):**
- `inWrapper`: show Settings > App's desktop rows only when true.
- `settings()` resolves to `{ server, hub, tray, closeToTray, launchAtLogin, startInTray, miniStyle, miniOnTop, ownTitlebar, glass, window, discordPresence, graphics }`. `graphics` is Graphics' mode (below): `auto`, `gpu` or `cpu`. `glass` is Settings › Appearance's **See-through window**; `window` is what `main` shows now (`glass`, below). `server` is the hub's address (`http://127.0.0.1:8484/` when this computer is the hub); `hub` is `local`, `remote` or null. `ownTitlebar` is null off Linux; `discordPresence` is null while the build has no Discord application; without a tray, Close always quits.
- `setSettings(patch)` takes any of those keys except `server`, `hub`, `tray` and `window` (`graphics` takes effect at the next start), plus `fullLook` (at once). Unknown keys are refused.
- `graphics`: what draws the page. `state` is `{ mode, software, light, fullLook, renderer, fellBack, ask }` (null until the app answered), and `on(fn)` hears every change; `line()` is Settings › App's line under the Graphics row. `desktop.js` applies it itself (`:root[data-graphics="light"]`, styled in `desktop.css`, which only the app loads).
- `glass`: the see-through window. `state` is `{ material, held }` (null until the app answered), and `on(fn)` hears every change. `desktop.js` asks for it itself.
- `openMini()`: the player bar's Device view button.
- `openClassic(handoff)` and `onClassic(fn)`: Classic mode (`web/screens/classic.js`), see below. An app older than the page rejects `openClassic`, and the page shows Webamp on its own stage instead.
- `windowAction('change-server')`: Settings > App, "Change hub…" (the welcome page).
- `updates`: this app's own version and updates (Settings > App, "This app", above "Your server"). `status()`, `check()` and `install()` resolve to `{ current, state: idle | checking | current | downloading | ready | failed, version?, received?, total?, error? }` (`install()` resolves to nothing: the app restarts; it rejects when the install failed); `on(fn)` hears every change. `check()` resolves once GitHub has answered; a download goes on, reported through `on`. Android's `window.LullNative.updates` has the same calls without `on` (android.md).
- `tailscale()` and `tailscaleServe()`, only when `hub` is `local`: Settings > App's "Reach this hub from anywhere" row (see Tailscale above). Both resolve to `{ installed, running, url, serving }`; `tailscaleServe()` rejects with Tailscale's own message. Call `tailscaleServe()` only from the listener's click: it changes their Tailscale.
- `front()` and `onFront(fn)`, `quiet()` and `onQuiet(fn)`: the UI sounds (ADR-0081), in `main`'s web UI. `front()` resolves to true while one of lull's windows has the focus (`main`, the mini player, the Classic window, native Classic's), and `onFront` hears `fn(true | false)` when that changes. `quiet()` resolves to true while the system asks for quiet (Windows: the sound scheme is No Sounds; GNOME: event sounds off; never elsewhere on Linux), and `onQuiet` hears each change. They exist only in the app (`inWrapper`), not in a browser or on Android (Android's quiet is `window.LullNative`'s, android.md). See Sounds below.

`desktop.js` does the rest itself in the wrapper: title bar, Ctrl+Shift+M, the close dialog, tray and mini-player actions, `set_now_playing`, and design and theme reports. It sends `set_now_playing` on player events, not as the song plays: a new position goes out only when it jumped.

## Behaviour worth knowing

- **Keep lull running when closed** (`keepRunning`, ADR-0090; behind the `keep-running` switch, which only shows the row; only when this computer is the hub):
  - it turns on Launch at login, and the login entry starts lull with `--background` (mod.rs), so it opens no window then. A start by hand still opens one;
  - Close hides `main`, tray or not. Opening lull again (a second launch) brings it back;
  - with no tray, Settings › App shows **Quit lull** (`windowAction('quit')`);
  - on mains power the computer doesn't sleep when idle while the switch is on (`awake.rs`). On Windows that's `SetThreadExecutionState` from one thread; on Linux, logind's sleep:idle inhibitor. On battery the OS decides, and a closed lid still sleeps.
- **Close:**
  - on a bundled page, or without a tray, it quits;
  - otherwise it hides `main`, asking once first. "Don't ask again" stores the answer as `closeToTray`;
  - setting **Close to tray** in Settings also counts as answered.
- **Mini player:**
  - opening it hides `main`; closing it (button, Alt+F4, tray) shows `main` again;
  - **Show lull** and **Classic mode** in the tray close it first;
  - a second launch focuses the mini player if one is open;
  - **its window is the device:** frameless and transparent, the page without any wallpaper (an unlayered, important rule in `wrapper.html`, since a design's wallpaper is unlayered CSS and beats `desktop.css`'s layer). It opens at 340×560 (device) or 540×90 (strip), then `desktop.js` sets its height to its design's player (`[data-dk-player]`), following it as it changes; the width is the design's;
  - the strip's wrapper keeps 18 px below it for the deepest design's shadow (glasshouse).
- **A listener's theme on the bundled pages** (`theme.rs`). These pages come from the app, so they can't fetch a theme stored on the hub: the hub's API isn't on their origin, it sends no CORS headers, and its cookie belongs to the hub's origin.
  - `main` has the theme loaded, so it hands it over as one package (`set_theme_package`): theme.css with each `url(assets/…)` inlined as a `data:` URL, which also spares a `url()` inside a custom property from resolving against whichever sheet uses it.
  - The app keeps the package for this run only, and says `theme-package { id }`. `wrapper.html` sets `Designs.packages` to ask `theme_package` before it boots. The package's CSS goes into the `user` layer as text, and its slots are sanitized as on the hub.
  - Without the package (the hub was down when the app started, or `main` hasn't loaded the theme yet) a page shows `base`, the built-in design the theme extends, and switches when `theme-package` comes. A theme that extends none falls back to lull.
  - An open mini player follows the edits: `theme.changed` reloads the theme in `main`, `main` hands it over again, and the mini player reloads it.
  - A bundled page in `main` asks `window_glass` when its theme asks for a see-through window. One that shows `base`, whose built-in design asks for none, leaves the stored request alone.
- **Taskbar buttons (Windows):** Previous, Play/Pause and Next under the thumbnail of `main` and of the Classic window (`ITaskbarList3`). They are added when Windows reports the window's taskbar button (`TaskbarButtonCreated`), show the latest `set_now_playing` (Play or Pause; greyed while idle or not connected), and click through `player::forward`. The glyphs are drawn at the display's small-icon size, dark on a light taskbar, white on a dark one.
- **System media overlay (Windows):** WebView2 gives the playing page a system media session from its `navigator.mediaSession`: title, artist, cover and Previous/Play/Pause/Next all work (checked through `GlobalSystemMediaTransportControlsSessionManager`). Windows names the session after `msedgewebview2.exe`, not lull, and Chromium passes no album. In Classic mode, `winamp.js` sets the session from the hand-off's titles and covers.
- **Classic mode:** the web UI's `/classic` hands the queue to `classic_open` and goes back to the page it came from. The Classic window (borderless, transparent, not resizable) loads `<hub>/desktop/winamp.html`, takes the handoff, starts Webamp where the app was, fits itself to Webamp's three windows, and moves by their title bars (`startDragging`). `main` hides and sleeps: WebView2's `IsVisible` off and its low memory target. Measured with a song paused: `main`'s renderer went from 2.4 s of CPU per 20 s (visible, its design's animations) to 0.18 s, its page tasks from 1.2 s to 0.005 s. Its page keeps running, so the listening history, Like and Save stay the web UI's. Closing Webamp, Alt+F4 or the tray's **Show lull** hands the queue, song, second, shuffle and repeat back; the tray's **Classic mode** brings the window forward.
- **Native Classic (test build, Windows and Linux):** with `LULL_CLASSIC=native` in the environment, `classic_open` opens `classic_native` instead of Webamp's window, and destroys `main`, so WebView2 (or WebKitGTK) can exit while Classic plays.
  - **The windows:** the main window, the equaliser and the playlist are a window each (no webview): on Windows Win32 popups, the main one on the taskbar owning the other two (`window.rs`); on Linux GTK windows on X11 or Wayland, the other two transient for the main one (`gtk_window.rs`); what they show and do is `ui.rs`, the same on both. Each is cut to the skin's `region.txt` shapes (a window region; GTK's input shape, and its visible shape without a compositor), as Winamp was, drawn at 1× from the `.wsz`; only what changed each frame is scaled by nearest neighbour into one bitmap a band of 64 rows high and copied to the window, so nothing a window's size is kept (at 3× a whole-window bitmap is 3.4 MB, and a layered window's compositor holds a second copy).
  - **Docking** (`dock.rs`, as Winamp 2: Webamp's snapping at Winamp's 10 px, at the screen's scale): a dragged window snaps to the others' edges and to the monitors' work areas, and windows whose edges touch are docked; dragging the main window moves everything docked to it, directly or through another, and dragging the equaliser or the playlist moves it alone, which is how it comes away. A window rolled up or down, or the playlist resized, moves what is docked to its bottom and right by the change; a new Classic size keeps the layout around the main window; a monitor gone or the work area changed brings any window left off every screen back. Wayland lets no app place its windows: there the compositor moves each, alone, and they don't dock. Where the windows were (the main window's place, the others' from it in skin pixels, open, rolled up, the playlist's size) is kept per device like the size: `lull:classicLayout`, from the hand-back to the next hand-off.
  - **Drawing:** the playlist's names in the skin's `pledit.txt` font (or Arial) at the screen's size, as the browser draws Webamp's: DirectWrite through Direct2D into the band, greyscale, 9 px, 0.5 px spacing, CSS's baseline, an ellipsis, the system's fallback fonts and colour emoji for what the font lacks. What shows follows Webamp's bundle and CSS, not Winamp's manual: stopped, no time and no analyser; title-bar buttons drawn only while held; one selected window (a click picks it); the bitmap font read as Webamp reads it (accents dropped, a blank cell for what it lacks, one cell per UTF-16 unit; curly quotes, dashes and full-width forms take their plain stand-ins where Webamp leaves a blank: a deliberate difference, the text the listener expects); slider frames, travels and thumbs at Webamp's roundings. Shade (a double click on a title bar, or its button) for all three, EQ and PL toggles and close buttons (the last window showing stays), Options menu (right click too: Skins from the favourites, Double Size, time remaining, Back to lull), the equaliser's ON, AUTO (lull's automatic level), PRESETS (lull's) and sliders, balance (Web Audio's equal-power panner; this window's alone, as the page has none), the marquee's words while a slider is held, the playlist's selection (click, Ctrl, Shift), double click to play, scroll, drag to reorder, Delete, its corner resizing it in Webamp's 25 × 29 px steps (the analyser in its visualiser's box while the main window is closed), and its ADD, REM, SEL, MISC and LIST pop-out menus as Webamp draws them (sort by title, reverse, randomize; what lull's queue has no use for, such as files from this computer or lists as files, says so in the marquee); all of Webamp's keys (Z X C V B and the keypad, R, S, arrows, Ctrl+D, Ctrl+R, Ctrl+T, Alt+W/G/E).
  - **The player** (`engine.rs`) decides by the web player's rules, on a 250 ms clock of its own. The rules themselves are one set: `web/player-rules.js` (which `web/app.js` follows) and `rules.rs` (which the engine follows) are tested against the same cases, `tests/player-rules.json`, and lining a better copy up is `web/align.js` ported step for step (`align.rs`) and tested against `tests/align.json`; a rule changed on one side fails CI until the other matches. The queue in the page's own shape (`queue.rs`: groups, picked copies, shuffle keeping next up, repeat off/all/one, radio top-up), listening history (`listen.rs`: a play at the first sound, seconds from position steps under 1.5 s, completed/skipped/stopped), the next song set within its lead of the playing one's end, gapless within 2 s of a song's end and Settings' crossfade (equal-power), prefetch and letting a dropped stream go, the hub's `stream` events (waiting states, a new attempt reopened where it was, a seek past what has arrived fetched from there or kept until it has (the hub's `ranges` and `seekAheadS`, ADR-0014; a kept seek's wait said only when long), a failed song skipped after 2.5 s, `choose` answered from a menu), ReplayGain or measured loudness, volume squared, lull Connect's state, and the better copy lined up as the page lines it up (`align.rs`; a copy with a longer intro looked for again, shifted), switched to at a quiet moment after `POST /switch`, faded in over 200 ms at the song's level and gliding to its own; three tries that didn't work out, or copies that don't line up, leave it to the next play. Sound: one output stream at the device's rate (cpal), each song in a deck (`deck.rs`: Symphonia, libopus for YouTube's Opus, resampled with rubato's FFT resampler) mixed by `mixer.rs`, then the device's equaliser (`lull:eq`, `eq.rs`, the same filters as Web Audio and Android).
  - **Beside Webamp:** `cargo test render_skins -- --ignored` (in `app/`) draws a folder of `.wsz` headless as the window draws them, and `tests/ui/classic-compare.mjs` draws the same scene with the vendored Webamp in Chromium and counts the differing pixels per window (`LULL_SCENE`: stopped, sliders, shaded, unicode, menus, resized, resized-even). Over 50 museum skins the main and equaliser windows are identical but for two skins, known Webamp bugs rather than regressions: `1a84bd0b4dd5ef859f1004bcbbe8c901`, 8 corner pixels at x 268–274 half-covered (Chromium's anti-aliased clip-path; native's region is hard-edged), and `ba89d964aaca373db4a43b084870c142`, the equaliser graph's middle row (y 142 of the stack, x 86–198) empty in Webamp, whose graph canvas never gets the base skin's pictures when a skin has no `eqmain.bmp`; playlists differ only in text anti-aliasing (Skia's tone curve, which DirectWrite can't match), and where a skin's empty `NormalBG` leaves Webamp's list see-through.
  - **Tests** drive the engine with a stand-in output and an in-process stand-in hub (`testhub.rs`): gapless with no silence, plays and their ends, a refused song skipped, prefetch, radio, repeat one, a reopened attempt, a better copy switched to, private listening, a held seek, the outbox's ops, lull Connect, Like; the shared cases above; what plays reported as the page reports it (`session.rs`), which the tray, the taskbar and Discord show; and Discord's presence over a stand-in for its pipe (`discord.rs`, on Linux).
  - **Around it** (`session.rs`): Like and Save from the tray (the engine's calls), the tray's, taskbar buttons' and Discord's now playing (`set_now_playing`), Windows' media overlay and media keys (the window's own System Media Transport Controls, named lull.exe, with the cover). Plays and likes the hub can't take become outbox ops.
  - **The handoff** adds `size`, `page` (the page Classic was opened from), `eq`, a kept-on-device skin's bytes (`skinData`, base64), the page's `repeatMode`, `radio` and `context`, and each song's `artistId`, `albumId`, `liked`, `saved`, `recommended`, `group`, `source`, `orig` and `gainDb`. A skin that fails leaves Webamp's base skin on (museum md5 `5e4f10275dcb1fb211d4a8b4f1bda236`, through the hub), which also fills a skin's missing sheets; the marquee says why.
  - **Leaving** (its close button, Alt+F4, Options › Back to lull, the tray's **Show lull**) builds `main` again on that page once the hub has heard about the last play, and the page takes the queue back with `classic_back` (`{ player, playing, eq, size, ops }`, `player` in `persist()`'s shape) through `takeBack`, which hands `player` to `P.adopt` (the restore every load runs): the equaliser and size are written, the ops go to its outbox.
  - **Measured** (release build, three windows, uncovered before and after each run): 22.6 to 24.7 MB in all at 1x, 2x and 3x (MP3, FLAC, Opus, AAC), no WebView2 process; playing steadily about 0.5 % of a core (the window's thread 0.26 %, the decoding 0.21 %), single 30 s runs 0.3 to 2 % as a song opens and settles.
  - **Discord** (a debug build only): `LULL_DISCORD_PIPE` names the pipes Discord's presence uses instead of `discord-ipc-`, so a test app can talk to a stand-in and never to the listener's own Discord.
  - **Linux:** CI's ubuntu-22.04 check job builds and tests it (clippy, `cargo test`, the bundles); the media keys and the desktop's media panel are MPRIS (`mpris.rs`, `org.mpris.MediaPlayer2.lull`), as Windows' are its media overlay. Not yet seen on a Linux desktop.
  - **Backlog: one player.** The rules are shared and tested on both sides, but two players still carry them out: the page's (`web/app.js`) and this engine. The lasting fix is the desktop's main window playing through this engine too (the page as its face, as Android's native player is), so the desktop has one player whichever window shows it. Not started.
- **Classic size** (1× to 3×, Settings › Appearance › Classic) is the Classic webview's page zoom (`classic_fit`): CSS pixels scale with it, so Webamp's own pointer math, title-bar drags and sliders stay exact, and its `image-rendering: pixelated` keeps skins sharp. A size the monitor's work area can't hold gives way to the largest that fits, with a note. An app older than `classic_fit` (0.2.0) stays at 1× and says so; the web page falls back to `setSize`.
- **Links:** every window's navigations and new-window requests go through `links.rs`: anything http(s) that isn't a bundled page or a hub this run opened opens in the default browser, redirects included. Last.fm's sign-in (`last.fm/api/auth`, reached by the hub's redirect) opens in the browser with its `cb` pointed at `http://127.0.0.1:<port>/lastfm`; when Last.fm sends the browser there, `main` loads the hub's own callback with that token and its cookie. A sign-in never finished keeps that listener's thread waiting until lull quits.
- **Discord:** with **Show what I'm playing on Discord** on, a thread speaks Discord's IPC (`discord-ipc-0..9`) as lull's public Discord application (`APPLICATION_ID` in `discord.rs`; no OAuth, no secret: each listener's own Discord client shows their presence). A "Listening to" activity (type 2): `details` the song (linked to its song.link), `state` the artist (linked to the artist's share page), the cover as the large picture with the album on hover (linked to the album's page), lull's glass badge as the small picture, start and end times (the progress bar), and the buttons "Open on song.link" and "Get lull" (other people see them; Discord hides them from the listener). Links and covers come from the hub's `GET /api/share/{track,artist,album}/{id}`, remembered per id for the run. Settings > App sets its look (`Look`, stored as `discord` in `settings.json`): what follows "Listening to" in the member list (`status_display_type`: song, the default; artist; or lull), the album cover (on; off shows lull's sky picture), the buttons (on), and a pause (hide it, the default; or show it with the paused badge and no progress bar). The thread waits 0.8 s for a burst of skips or seeks to settle and sends only what Discord would show differently (a start moved by under 2 s doesn't count): Discord allows 5 changes per 20 s. Without Discord it looks again every 20 s while a song plays. Nothing in lull reacts to games: Discord keeps one activity per application, so a game's own activity sits beside lull's. The pictures are `app/discord/*.png`, made from the SVGs there by `uv run app/discord/render.py` and fetched by Discord from GitHub (`raw.githubusercontent.com`, through Discord's media proxy, which caches them).
- **Tray glyph (Windows):** follows the taskbar theme (`SystemUsesLightTheme`), not the app theme. A thread waits on the registry key, because Tauri's ThemeChanged only tracks the app theme. Its size follows the primary monitor's scale.
- **Linux:**
  - **Tray:** only with a StatusNotifier host on D-Bus; without one there's no tray and Close quits. The tray always gets `tray-dark-32.png`: Tauri hands AppIndicator a file, so a themed icon name can't be used.
  - **Title bar:** native by default. With **Use lull title bar** (`ownTitlebar`, restart), the window is undecorated and draws GNOME header-bar buttons in the order of `button-layout`.
  - **Mini player:** opaque `--sky` fallback without a compositor. On Wayland it shows a one-time note about Always on Top.
  - **Media keys:** grabbed with global shortcuts only when the web UI reports no `navigator.mediaSession` (X11 only). Windows never grabs them: SMTC handles them through Media Session. That path works only while a media element plays: Chromium gives a page a system media session only then. Verified on Windows with a Jellyfin song: Play/Pause, Next, Previous and Stop all reach the web UI's own handlers.
- **A see-through `main`** (`glass.rs`, docs/themes.md section 12):
  - **The request.** The theme in use asks through `window_glass`: its materials in its order, for the mode shown. `designs.js` resolves theme.json's `window`, and `desktop.js` asks again whenever the theme or its mode changes.
  - **The grant.** The app grants the first material this computer draws without lag, unless **See-through window** is off (`held: off`), Windows' Transparency effects are off or the page reports `prefers-reduced-transparency` (`system`), none is drawable (`unsupported`), or Linux made `main` solid (`restart`). The page sets `:root[data-window]` from the answer, and from the `glass` event when the listener's switch or the system changes it.
  - **Kept for the next launch.** The request is stored as `window` in `settings.json`, so the next launch opens `main` as the theme wants it.
  - **Windows.** `main` changes live: blur-behind with an empty region lets the page's alpha through, the webview's background turns clear (solid white again when off), and window-vibrancy draws the material. Mica and Acrylic also extend the frame over the whole window, because the system draws them in the frame.
    - What each Windows draws without lag: Mica from build 22000; Acrylic from 22523, as a system backdrop; plain blur only on Windows 10; clear everywhere.
    - Acrylic before 22523 and plain blur on Windows 11 go through the old accent policy, whose window trails the pointer when dragged.
    - Measured on Windows 10 22H2 (165 Hz). A script moved `main` across 400 px, then resized it by 220×160 px, 60 times a second for 5 s each, timing how long DWM took to show each step (`DwmFlush`):

      | `main` | Moving: average, 95th percentile, steps over 1.5 refreshes | Resizing: the same |
      |---|---|---|
      | made opaque (as 0.2.1), solid theme | 4.2 ms, 6.9 ms, 0% | 6.1 ms, 8.9 ms, 5% |
      | made transparent, solid theme | 4.2 ms, 6.8 ms, 0% | 6.5 ms, 9.3 ms, 7% |
      | clear | 4.7 ms, 7.4 ms, 0% | 6.7 ms, 9.3 ms, 7% |
      | blur (two runs) | 4.7–4.8 ms, 7.4–7.5 ms, 0% | 6.9–7.1 ms, 9.3–9.6 ms, 9–12% |
      | acrylic (accent policy) | 10.3 ms, 13.0 ms, 71% | 17.7 ms, 18.5 ms, 97% |

    - Idle, with nothing moving, lull's own processes used the same few tens of ms of CPU per 20 s with glass or without, and no GPU. DWM redraws the blur only when something behind the window changes.
    - The Personalize registry watch (`follow_personalize`) also follows Transparency effects.
  - **Linux.** A window gets an alpha channel only when it is made. `main` is made with one when the stored request would be granted (a compositor is needed). Blur is KWin's `_KDE_NET_WM_BLUR_BEHIND_REGION` on X11; GNOME and Wayland get clear glass only.
  - **The title bar.** On Windows it is always lull's own, so nothing changes. On Linux the native frame or lull's own (`ownTitlebar`) stays as set.
  - **Bundled pages** in `main` (welcome, unreachable) don't take part: they paint their wallpaper, so the window looks solid.
- **Graphics** (`graphics.rs`, Settings › App › Graphics, ADR-0063): **Automatic**, **Use the graphics card** or **Processor only**.
  - **Why:** a listener on an NVIDIA laptop saw lull 0.2.5's AppImage draw at about 2 frames a second, while a computer with no graphics card at all runs it smoothly. WebKitGTK falls back to the processor quietly (no usable EGL, a software GL such as llvmpipe, or `WEBKIT_DISABLE_DMABUF_RENDERER`, which since 2.44 turns its GPU path off altogether), and lull set nothing about it.
  - **Before anything else:** the choice is read from `settings.json` first thing in `desktop::run`, before Tauri or any thread starts (the config folder found as Tauri finds it), because WebKitGTK reads its switches from the environment and the page's process inherits them. It takes a restart to change; Settings offers **Restart now**.
  - **Linux** (`platform/linux_graphics.rs`): Automatic changes nothing. The graphics card clears the switches that turn the GPU off (`WEBKIT_DISABLE_COMPOSITING_MODE`, `WEBKIT_DISABLE_DMABUF_RENDERER`, `WEBKIT_SKIA_ENABLE_CPU_RENDERING`, `LIBGL_ALWAYS_SOFTWARE`, a desktop entry's or the listener's), and on a laptop with two cards (two in `/sys/class/drm`, one that showed the boot screen) renders on the other: NVIDIA's driver takes its render offload switches (`__NV_PRIME_RENDER_OFFLOAD`, `__GLX_VENDOR_LIBRARY_NAME`, `__VK_LAYER_NV_optimus`, what `prime-run` and switcheroo-control set), Mesa's `DRI_PRIME=1`, and WebKit is pointed at that card's render node (`WEBKIT_WEB_RENDER_DEVICE_FILE`), since it renders on the display card's otherwise. A card without a driver bound is never chosen. The processor only sets `WEBKIT_DISABLE_COMPOSITING_MODE`, `WEBKIT_DISABLE_DMABUF_RENDERER`, `WEBKIT_SKIA_ENABLE_CPU_RENDERING` and `LIBGL_ALWAYS_SOFTWARE`, and loads Mesa's EGL alone where it is installed (`__EGL_VENDOR_LIBRARY_FILENAMES`, only naming a file that exists: glvnd with none would leave no EGL), so a driver that crashes is never loaded. The browser lull opens links in gets the environment lull was started with.
  - **Windows** (`platform/windows.rs`): WebView2's browser arguments, after wry's own: the graphics card `--ignore-gpu-blocklist --force-high-performance-gpu` (ANGLE takes the high-performance adapter where there are two); the processor `--disable-gpu`. Windows' per-app GPU preference can't be used: it is keyed by the program's path, and WebView2's is the shared runtime's, which changes with every runtime update.
  - **What draws the page:** WebKitGTK's page scripts can't tell (WebGL's renderer always reads "Apple GPU"), so on Linux the app reads the engine's own report, `webkit://gpu`, once a run in a hidden webview after `main`'s first page: the processor draws when the policy is never, when WebKitGTK 2.44 or later has no DMA-BUF renderer, or when the page's GL renderer is a software one (llvmpipe, softpipe, swrast). WebView2 tells the page the truth, so on Windows the page reports WebGL's renderer (SwiftShader, the Basic Render Driver, or no WebGL: the processor). The finding goes in `logs/webview.log`, after the line saying what the mode set, with what paces WebKitGTK's frames and how often (its VBlank source and rate: a 144 Hz screen gets 144 frames a second only when that says 144).
  - **The lighter look:** where the processor draws (and always under Processor only), every page gets `:root[data-graphics="light"]`: `desktop.css` stops all movement and every `backdrop-filter`, decorative loops hold still (`App.still('graphics')`) and `App.reducedMotion()` is true (`desktop.js` wraps it). Both live in the app's own files, so a browser loads none of it. Settings › App says so in one line, with **Use the full look** (`fullLook`, kept in `settings.json`; then **Use the lighter look**). The last look is kept on the device (`lull:graphicsLight`), so a page opens in it.
  - **Never locked out:** a start in a chosen mode is on trial from when `main` shows (or its page dies, shown or not) until the listener's first click or key in it (`graphics_used`). The trial is written to `settings.json` (`graphicsTrial`) as it begins and cleared as it ends, so one still there at the next start (a blank window, a crash at start, the listener giving up) sends that start back to Automatic; Settings says "The last start with “Use the graphics card” didn't come up, so lull went back to Automatic." (or “Processor only”) until the listener chooses again. Automatic is never on trial: it is what lull did before the setting.
- **Sounds** (`sounds.rs`, ADR-0081): `main`'s page plays every UI sound, the mini player's presses and Classic mode's included, while `main` itself may be hidden, so the app tells it two things:
  - **In front:** every Tauri window's focus change wakes a thread that waits until the focus has stayed put for 150 ms (moving from `main` to the mini player is one window losing it and another taking it), then asks the system and says `window-front` if the answer changed. Windows: the foreground window is this process's and shows (the tray's hidden window, in front while its menu is open, doesn't count). Linux: any of this process's GTK windows is active. Both count native Classic's windows; `main` doesn't exist while they're open, and its new page asks `window_front` when it loads.
  - **Quiet:** Windows' sound scheme (`HKCU\AppEvents\Schemes`' default value is `.None`, "No Sounds"), followed by a registry watch like the Personalize one; GNOME's `org.gnome.desktop.sound event-sounds` off, followed through GSettings (no other Linux desktop has a switch lull reads).
- **Window state:** the plugin restores size, position and maximised for `main`, `mini`, `strip` and `classic` (the mini player's and Classic's pages then fit their size). Visibility and decorations are always the wrapper's choice.

## Known limits

- The Snap Layouts flyout on the custom Maximise button doesn't appear (DESKTOP.md 2.1).
- Pages from other origins get no IPC.
- In the Classic window Webamp's windows stay docked together (the window moves instead), and its double-click on a title bar (window shade) is lost to the drag. Skins are chosen in Settings › Appearance › Classic, in `main`; the window follows a new choice at once (the `storage` event, docs/context/skins.md), shows Webamp's own Skins menu (favourites), and takes dropped `.wsz` files for that session only. Webamp's alerts show as a note over its windows, never as a dialog.
