# Progressive streaming and peer fallback

How `GET /api/stream/{trackId}` plays a song while slskd is still downloading it, and from wherever the listener seeks (`fetch.rs`, `fetch/legs.rs`, `ranges.rs`, `stream.rs`, `range.rs`, `layout.rs` in `crates/soulseek`; ADR-0014).

## Fetches

A **fetch** gets one song onto disk. There is at most one live fetch per track and streaming profile, shared by everyone who wants the song (the player streaming it, a save completing it, a [preload](#preloading)), so the bytes cross the network once.

**Presets** (ADR-0017). Every request streams by the source preset of the device that asks (`Rules::profile_for`: its choice, else Phone for a phone and Desktop otherwise, [api.md](api.md) `GET /api/sources/presets`), and a fetch keeps the profile it was started for (`Fetch::profile`) for all it decides: its start, start fast's race, fallbacks, its better copy, preloads and later plays from the cache. Fetches are kept per song and profile (`Key`):
- devices whose presets hold the same profile share one fetch, as before;
- a device of another profile joins a running fetch when it has the copy that device picked, or a copy that suits its profile (`policy::suits`: a format it leaves on, within its cap, passing its minimum) or that its own fetch would take first anyway (`first_choice`); the live map then keeps the fetch under that device's key too. A better copy is offered to them only when it is worth switching to by every profile playing it. One device moving on (`DELETE`, switching copy) lets go of its key; the fetch carries on for the other;
- otherwise the device gets its own fetch, which never takes a copy another profile's fetch of the song is transferring (`held_elsewhere`), so one copy never downloads twice at once. With only such a copy left it fails, saying another device's preset is fetching it, and playing the song again joins or reads it.

The cache may then hold a copy for each, and each later play takes the best its own preset allows (`best_cached`). A preset changed while a song plays applies from the next opening.

Openings of the song's stream (`Fetcher::stream`) take turns, so two at once join one fetch. Before, each could find no fetch running and start its own; start fast's race then handed the song to Soulseek's copy as the first one's, and a player following the second dropped every event of the copy playing: what had arrived froze on the seek bar, with no speed, and seeks past it were kept and never landed while the song played on (2026-11-08). Two openings at once can come from the player and a download to the device, the player's reopening on every (re)connect of the event stream, or two devices.

A finished copy already in the stream cache plays at once, whatever the `below` rule (never one in a format streaming switched off, [soulseek.md](soulseek.md#source-rules)), with one `stream` event (`streaming`, and `belowMinimum` when it doesn't pass the streaming minimum). Otherwise:

1. **Pick a source.** The listener's pick (`?peer=&path=`: a copy a search found, or one finished in the cache, `Fetcher::picked`; a search's copies are kept 6 hours, a pick as long as its queue entry) comes first, then the first untried copy that passes the profile's minimum, in its order ([soulseek.md](soulseek.md#source-rules)): the streaming profile when the player started the fetch, the saving one when a save did. With no known source the fetch searches for the song first (`finding`).
2. **None passes.** When copies exist but none passes the minimum, the profile's `below` decides:
   - `playBest`: the best of them plays; the `stream` event says `belowMinimum: true`, so the player can show a badge;
   - `keepLooking`: search again, up to 3 searches 20 s apart, then fail with "no copy meets your streaming minimum";
   - `ask`: the fetch waits as `choose`, with the copies found in the `stream` event's `choices` (up to 8). The listener answers by playing one (`?peer=&path=`), which replaces the fetch, or by skipping; after 10 minutes it fails;
   - a save's fallback (`saveBestUpgrade`) takes the best one; under `wait` and `ask` library decided before starting ([save-flow.md](save-flow.md)), so the fetch fails rather than save a copy below the minimum.
3. **Make room** in the cache for the file twice over (lull's copy and slskd's file for the leg running, [cache.md](cache.md)), then get it in [legs](#legs).
4. **Watch each leg every second**, and give up on this peer when:
   - **no byte has come within 6 s of the request** (`race::FIRST_BYTE`, ADR-0018), queued at the peer or not, for a copy lull chose itself: a song's start, a preload. A song's start holds one lane of the hub's budget until its first byte ([Better copies](#better-copies)). The listener's own pick, and a copy a save named, keep the older patience: 20 s to accept, 30 s queued (`PATIENT_QUEUE`);
   - no new bytes have arrived for Settings › Sources' stall timeout (`stallTimeout`, 15 s by default; shown as `stalled` after 5 s);
   - slskd reports the transfer failed;
   - after 10 s of sending it delivers under 1.25 times the song's rate (its size over its length) and an untried copy is expected to be twice as fast (ADR-0015, [soulseek.md](soulseek.md#ranking)); not for a copy the listener picked or a save named, and not remembered as a stall.

   However it ends, a transfer that sent 1 MB or for 10 s leaves its rate in the peer's record.
5. **Fall back** to the next copy in the same order. A stall is remembered against the peer (ranking demotes it); an offline peer or a long queue is not. A song's start gives up after 5 peers, asked one at a time. Peers whose queue is longer than `maxPeerQueue` are never picked automatically. A preload goes for the preset's highest band first (`policy::band`), in the usual order within it.
6. **Done:** every byte of the copy is in lull's file, which the cache records as complete. The last leg's tail is read from where slskd moved its file: slskd marks a transfer Succeeded before it moves the file and raises `DownloadFileComplete`, so lull asks for the path again each second, for up to 60 s, rather than failing the song in that moment.

**YouTube.** With Settings › Sources › YouTube on, the player's fetch (and a preload) turns to YouTube when no peer delivers, or none starts within `waitS` (`fallback`), or races YouTube against Soulseek's copy, whichever sends first playing (`startFast`). The YouTube copy is one more attempt (`attempt` goes up), written into the cache and served the same way: [youtube.md](youtube.md#modes). YouTube's copy is never a better copy: Opus 160 is in the lower band, so it is only ever beaten.

**Handing over before the first byte.** When start fast's race goes to Soulseek, its fetch takes the player's fetch's place (`hand_over`): a response still waiting on the player's fetch serves the Soulseek one instead (`Fetch::successor`), its `stream` events name the job they replace (`replaces`), and the player's fetch ends `cancelled` with a note saying why.

**Better copies.** See [Better copies](#better-copies): a copy in a higher quality band is raced for beside the one playing, and the player switches without a jump.

**Switching source mid-song.** `GET /api/stream/{id}?peer=&path=` with another copy than the one playing replaces the fetch: the old one is cancelled, unless a save is completing it; then it runs on for the save, out of the player's way (no more `stream` events). The old response ends; the player opens the new one and seeks back by time (ADR-0008).

**Stopping.** `DELETE /api/stream/{id}` (skip, next) cancels the fetch unless a save still needs it or a device lists it to preload; a better copy still racing for switching stops too, its lanes cancelled and their files forgotten, unless a save needs it. A kept queue that has started sending runs on for later plays. Start fast's Soulseek copy runs on: it is for later plays and saves as much as for this one. lull's file keeps what arrived, with its ranges, and asking for the song again fetches only what is missing.

**Events.** Each change publishes:
- `stream` (to the player, only while it streams);
- `transfer`;
- `job` (an Activity row).

Stream status follows the fetch: `finding → queued → buffering` (under 256 KB from the leg running) `→ streaming`, with `stalled`, `fallback`, `choose` and `failed`.

## Legs

A Soulseek copy arrives in **legs** (`fetch/legs.rs`, ADR-0014): each is one slskd transfer of the file that starts at a byte lull picks.
- **Starting one at X.** lull makes slskd's incomplete file exactly X bytes long, a hole (under both spellings of its path, [below](#where-the-bytes-are)), then queues the download. slskd 0.26 resumes a download from its incomplete file's length on every attempt (`retry.partial: resume`, its default), so the peer sends from X. It reads that length once, when it sends the request, so the file is sized before the request and not touched after. On Windows, a leg just cancelled may still hold its file a moment; lull waits up to 10 s for slskd to let go before sizing it again. The contract test (`tests/slskd-contract/`, CI's `slskd-contract` workflow) runs the image `deploy/compose.yaml` pins, and on Windows the binary `app/build.rs` pins, against a stand-in server and peer. It fails if the peer isn't asked for X, or if the incomplete file can't be read while slskd downloads it and kept open while slskd moves it. Stock slskd forbids that read on Windows (error 32), so the Windows app bundles lull's build of it (ADR-0062).
- **Copying.** Every 250 ms what slskd wrote of the leg is copied into lull's own file for the copy (`<transfers>/lull/<user>/<remote folders>/<file>`), at its own offsets, and added to the copy's `Ranges`. slskd reports a download done just before it moves the file to `<downloads>/<last remote folder>/<file>` and names that path in its `DownloadFileComplete` event; lull copies the rest from the leg's open file, else from there, waiting up to 60 s for the event, then removes slskd's file and transfer record. The ranges are written to the cache index every megabyte and when a leg ends.
- **Which byte.** The first missing one; a leg that reaches bytes that arrived before stops (it has nothing new). A reader waiting for a byte that hasn't arrived asks for it (`Fetch::ask_for`, while it waits: a request the browser drops asks nothing). When that ask has stood 300 ms (the reads of one seek come together):
  - **Another peer first.** If the leg running wouldn't bring the byte within 10 s at slskd's reported speed (`JUMP_S`; behind the leg is never), another peer with the same file starts a leg there, beside the first one, which keeps running and keeps its slot. Same file means the same size and kind, a free slot in its search answer, no stall on record and not tried for this copy. Its bytes are served at once but kept apart until checked: where the two legs meet, the first peer's bytes are compared with the other's. 64 KiB the same, and the other peer's bytes become the copy's, and the first leg stops there. Any difference, and they are dropped (to be fetched again from the first peer), its leg is cancelled and that peer isn't asked again for this copy. A leg of another peer that fails just ends; it never fails the song.
  - **Otherwise the same peer.** With no other peer, if the leg running wouldn't bring the byte within 30 s (`JUMP_SAME_S`), the same peer starts over there: the leg is cancelled and a new one starts at the byte. After that leg reaches the end, the gap it left fills from its start.
- **When a jump is allowed.** It gives the peer's upload slot back, so only when slskd resumes where lull sizes the file, the peer's search answer said it had a free slot, and no leg of this copy has waited in its queue. And only in a file the browser seeks with one read: MP3, M4A (its index at the end is fetched by a leg too), a FLAC file with a SEEKTABLE block. A FLAC file without one, and Ogg, are bisected, a dozen reads one after another that would each start a leg, so they wait for the transfer instead; a FLAC file's block headers are read as they arrive, and until they have, it doesn't jump. `stream` events carry `seekAheadS`: 10 while another peer can take a jump, 30 while only the same peer can, `null` while neither can, so the player chooses between going to a seek now and keeping it ([web.md](web.md)).
- **An slskd set to overwrite** (`retry.partial: overwrite`, possible on an existing slskd): it starts a leg over from byte 0. lull sees it (the file shorter than X, or its first bytes no longer the hole) and copies that leg from 0, which is still the copy's own bytes. Seeking ahead is then off until the hub restarts, and legs run to the end rather than stop at bytes that arrived.

## A song's outcome

Why a song stopped is its job's: the fetch's progress (`status`, `error`) is the one record, which `stream` events, Activity's `job` rows and `GET /api/jobs` all show. The player adds no reason of its own.
- **The hub failed the song** (no peer delivered it, YouTube found nothing): the job's `failed` event carries the hub's sentence, YouTube's part included.
- **The player's audio failed** (a 502 the player can't read, a copy its browser or app can't decode, a response that broke off): it tells the hub, `POST /api/stream/{trackId}/output-error { jobId? }` (`Fetcher::output_error`). A failed job answers with its own event, unchanged. One whose copy arrived records that this device can't play it (`unplayable`: "this copy can't be played in <device> (<format>)") on the job, for Activity, and answers with that; other devices' playback is untouched. Without a job id (the audio failed before the player heard of its job), the song's live job answers, else its latest. Nothing is started or restarted.
- **The hub can't be reached:** the one sentence the player says itself ("Can't reach the lull server").

Once a song has failed, it stays failed. The job's earlier events (its opening `finding`, say) come on the event stream, and the outcome comes on the play's own request, so an event can arrive after the outcome. The player ignores any of them that isn't a newer `attempt`.

Before (2026-11-05), the player's own "No peer delivered this song" covered every failure it hadn't heard the hub's reason for, a browser's decode error included.

## Better copies

When the song plays a lesser copy, a better one is raced for beside it, and the player switches to the winner mid-song without an audible jump (ADR-0013, ADR-0018). Settings › Sources › "Switch to a better copy while a song plays" (`sources.switchToBetter`, on by default) turns it off.

- **Bands.** A better copy is a higher **quality band** than the copy playing (`lull_core::quality::Band`: `Lossless`, `HighLossy` at 220 kbps and up, so V0 counts with 320, and `LowerLossy`; a bitrate lull only estimated from size and length counts one band down). The device's preset decides which bands are allowed (`StreamProfile::bands`: no lossless under a cap, a band needs a format left on, `LowerLossy` only when the minimum is under 220). So Opus 160 to MP3 192 is no switch, Opus 160 to 320 is, and 256 to 320 no longer is (before 2026-11-12 it was, by `Quality::beats`). `policy::switch_to` and `policy::better` say so; a copy must also pass the minimum and be within the cap.
- **When it starts.** Whenever the policy knows a copy in a higher band, on opening the song (a preload or cached copy it joins included) and on each new attempt, and when the copy playing fails the minimum and the song hasn't been searched during this play (the upgrade then searches again, once, in the `Prefetch` lane of the [search budget](soulseek.md#search-budget), and gives up quietly when nothing turns up). Never for a copy the listener picked. It is an upgrade fetch (`Slot::Upgrade`, out of the player's way). The playing fetch is never touched by the race: its source, attempt and job stay as they are until the player switches (`adopt`).
- **The race** (`fetch/race.rs` runs it, `fetch/plan.rs` reads the preset and orders it; ADR-0018):
  1. **Rounds.** The candidates are one copy per peer, its best, grouped by band, highest first, never the playing copy's band or lower; within a band, a free slot first, then the speed lull measured (ADR-0015), then the speed the peer reports, which only breaks ties.
  2. **Lanes.** A round runs up to 3 lanes at once, each a request to a distinct peer, and asks at most 6 peers. A lane with no byte within 6 s of its request, queued at the peer or not, gives way to the next candidate; a lane is cancelled before its replacement is requested. When a round fails, the next band down runs, never to the playing copy's band.
  3. **The speed gate** counts lull's own bytes on the lane, never slskd's or the peer's figure: once a lane has sent for 3 s it passes when the bytes of its last 2 s are at least `OUTRUN` (1.5) times what the song plays in 2 s (size over length); a copy that has all arrived passes. A lane that has sent for 10 s (`SLOW_AFTER`) without passing gives way. `OUTRUN` is also the upgrade's ready rule.
  4. **The first lane to pass wins.** The others are cancelled at once and their partial files deleted, never cached; the cache index never records them. The winner's running transfer goes to the upgrade fetch, which carries on from it and never requests it again.
  5. **No band sends.** One queue is kept while the song plays: the shortest at the best band tried. If it starts sending and passes the gate it is the winner; one that sends but never outruns the song runs on, unoffered, for the next play. At the song's end a copy that is sending finishes; a mere queue place is left (`Fetcher::stop_streaming`).
  6. **Politeness.** A peer whose upload lull cancelled while it was sending 3 times today isn't raced (`lanes::CANCELS_A_DAY`), though it can still start a song or be picked.
  7. **One race per play** (`Fetch::raced`). After the player switched, or the race failed, no other race runs for this play, even if a higher band turns up. A winner that turns out not to be the song (ADR-0016) frees the race for one more.
  8. **Said once.** One log line per race (song, bands tried, lanes asked, winner, seconds, cancels). When the song stays on its copy the playing job's note says why, starting "Stays on this copy: " (Activity shows it).
- **The lane budget** (`fetch/lanes.rs`). A hub-wide 4 lanes serve every song at once: a lane is a request that hasn't sent a byte yet, whether a race's, a song's start or a preload's ask. When lanes free up at one moment, a playing song's start takes them first, then a better copy raced for a playing song, then preloads. A preload takes one lane and asks one peer at a time.
- **The offer.** The playing song's `stream` events carry `upgrade { peer, path, format, status, received, size, ready }` only once a lane has won; it names the winner and is `ready: true` from its first event (`Fetch::won`). Never while lanes race. A finished upgrade stays in the map while the player streams the song, so it can be switched to. The next song's stream opens before it plays (gapless, crossfade): the player keeps its latest event and applies it when the song hands over, since the hub sends nothing more for a finished copy ([web.md](web.md#better-copies)).
- **A pick is its fetch.** Asking for the song with the copy the listener picked (the player reopens it after every fallback, the pick still in its address) joins the fetch that pick started, whichever peer sends now; only another copy replaces it. Before, a pick whose peer stalled was replaced by a fresh fetch from that peer on every reopen, in a loop (1,400 fetches for one song, 2026-11-05). The player follows only the fetch its own opening adopted: events of another fetch of the song are not this play's.
- **The switch.** The player plays the copy silently from `GET /api/stream/{id}/copy?peer=&path=` (serves whichever fetch holds that copy, changing nothing), lines it up, and calls `POST /api/stream/{id}/switch { peer, path }` right before its crossfade: the upgrade becomes the song's live fetch, and the copy before it stops once its last response ends (at most 60 s later), unless a save needs it. The answer is the song's `stream` event as it is now, its events name the job they replace (`replaces`), and its job's note says "switched to <format> from <peer>" for Activity. A manual pick of the same copy adopts it too (`?peer=&path=`). A seek anywhere keeps the listener's place before, during and after it; a loser's file is never served.
- **Where it picks up.** At the point the song has reached, lined up to the sample, never from the copy's start ([web.md](web.md#better-copies)).
- **A better copy that isn't the song.** Every Soulseek copy that arrives is checked by its sound (ADR-0016). One beside the song the player streams that fails leaves that place, and the next copy worth switching to is fetched (`check_soulseek_copy`, `better_later`).
- **When the player can't line them up**, nothing changes mid-song and the better copy plays from the next play: the cache's choice is the best copy, not the latest ([cache.md](cache.md)). The player says why (`POST /api/stream/{id}/not-switched`), and the copy's job note shows it in Activity.
- **Preloads.** A song whose cached copy the policy knows a higher band than is preloaded again (`better_than_cached`), so it plays that from its start.
- **Saves.** `save_candidate` reuses the better copy on its way (or finished) before the one playing.

Before 2026-11-12 the better copy was fetched one peer at a time (up to 5, each 20 s to accept and 30 s queued, dropped at once when YouTube was ready) and a fifth more bitrate was a switch; a listener could wait minutes for a copy that never came.

## Preloading

So that next plays at once, the player lists the songs queued after the current one with `PUT /api/stream/prefetch { tracks }` (`prefetch.rs`): at most 3, in queue order, as many as `playback.prefetchCount` (0-3, default 2). Each call replaces the calling device's list (the gate's device id; requests without one share a list), preloaded by that device's preset.

- **What starts.** In order, each listed song that isn't saved, finished in the cache or already fetching gets a fetch. Its search runs in the `Prefetch` lane of the search budget, behind the player's searches ([soulseek.md](soulseek.md#search-budget)), and is skipped when one already found copies. The fetch then waits (up to 30 s) while the playing song is still finding a copy or waiting for its first bytes, and the next song waits until this one's bytes flow (up to 30 s), so one peer at a time is asked, each with the 6 s rule, for the preset's highest band first ([Better copies](#better-copies)).
- **Quietly.** A preload publishes no `stream` events (`transfer` and `job` as usual) and never waits as `choose`. When no copy passes the streaming minimum it starts only under `playBest`; under `keepLooking` or `ask` it doesn't start (or, after fallbacks, fails), and the player's own fetch applies the rule when the song plays. Songs no peer shares are left to the player too.
- **Let go.** A song no device lists any more is cancelled after 10 s, unless by then the player streams it, a save needs it or a device lists it again; the grace lets the player open the next song before or after sending its new list. A finished preload leaves the live fetches at once, so its file is an ordinary unpinned cache entry ([cache.md](cache.md)), newest in the eviction order.
- **Playing it.** `GET /api/stream/{id}` joins a running preload, with one `stream` event saying where it stands, and from then on it is the player's fetch (`below` rules included). A finished one plays from the cache at once.

## Where the bytes are

`LULL_TRANSFERS_DIR` is the folder holding slskd's incomplete and downloads folders, as lull sees it.
- **Folder names.** lull reads slskd's folder names from `GET /options` (administrator key); without it, it assumes the kit's `/transfers/{incomplete,complete}`. A folder lull can't see turns the `soulseek` status to `warn`.
- **Incomplete path.** slskd 0.26 writes a running download to `<incomplete>/<user>/<remote folders>/<file>`, with the peer's root (`@@abcde`, `C:\`, `\\server`) dropped. Each segment is sanitised: `/` and NUL become `_` on Linux slskd; Windows slskd also replaces `<>:"|?*`, so both spellings are tried.
- **How it's written.** slskd appends from where the leg starts and never sizes the file up front. lull reads the spelling that changed from how it left it. slskd's lock is advisory on Linux, so lull opens it read-only and takes no lock. What has arrived is the copy's `Ranges`, never a file's length.

## Serving bytes

- **Before answering.** The response waits until the fetch has a source (which gives the size and type) and its ranges hold the requested start, asking for that byte while it waits ([Legs](#legs)). Any range inside the file waits as long as the fetch keeps trying, a request from byte 0 or a seek ahead of the transfer alike: those bytes are coming, so the browser buffers rather than failing (its time-to-byte guess for VBR files or a big embedded cover can land past what the player thought had arrived). Only a range past the end of the file, or one a finished file turned out too short for, answers 416 (`Content-Range: bytes */size`). When another source took over meanwhile (a fallback, YouTube), the size and type are worked out again before answering.
- **Ranges.** They resolve against the file's full size from the search (`range.rs`): 200 for no range, 206 for one range, and suffix ranges are supported. Multi-range and malformed headers get the whole file.
- **The body.** It reads at most 64 KiB at a time, never past the end of the range it is in (`range::sendable`), then waits at the gap, asking for the byte there. Memory per response is one chunk.
- **When the file is recreated.** A Soulseek copy's file is lull's and never moves. A YouTube copy's may be recreated by yt-dlp: whenever the ranges hold bytes the open handle doesn't show, or the handle fails while the transfer runs, the reader reopens by path at the same position (on a Windows host, Docker Desktop leaves old handles on the old copy).
- **Fallback ends a response** with an error, since another peer's file has different bytes. The player sees the `stream` fallback event, reopens the stream URL and seeks back by time.
- **Saved tracks** stream from the library crate (`/api/library/stream/{id}`), not here.
