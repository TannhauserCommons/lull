# Quality: the queue, web assets, visual matrix, budgets

Owned by the Quality session. Files: `scripts/web-dist/`, `crates/server/src/web.rs`, the web stage of the `Dockerfile`, `tests/ui/`, `.github/workflows/` and `scripts/queue.sh`, `ship.sh` and `release.sh`.

## The queue: main is always green

Main moves only through the queue (ADR-0095). `mise run ship <topic>` pushes `HEAD` to `queue/<topic>` and waits for the verdict on that commit: landed, or red with the run's link. Red leaves main untouched; fix it on your branch and ship again.

- **One run at a time** (`.github/workflows/queue.yml`, on main, started by `queue-kick.yml`): `scripts/queue.sh plan` rebases every waiting branch, oldest first, onto main and the ones before it. That stack is the candidate. A branch that doesn't rebase cleanly onto main is set aside red ("conflicts with main"). One that conflicts only with a branch stacked ahead of it waits, not red ("waits for queue/<topic>"), and the run after that branch's verdict tries it again: rebased onto main once that branch lands, where a real conflict then goes red. A workflow file (`.github/workflows/`) reaches a candidate only exactly as its topic pushed it: GitHub refuses the job's token any other version. So two topics changing the same workflow go one after the other ("waits to go alone"), and one whose workflow main changed since is red until rebased and pushed again. A candidate GitHub refuses anyway fails the run without holding the queue: a batch splits, a single topic goes red with GitHub's reason.
- **Only the checks its diff needs** (`checks` in `queue.sh`): `ci` for anything but docs, `design/`, `fastlane/` and `site/`; `ui-gates` for `web/` and `tests/ui/`; `graphics` (the Linux app with no graphics card, Graphics below) for `app/`, `web/`, `tests/desktop/` and the fixture hub; `aur` (lull-bin built, installed and started on Arch against the newest release, desktop.md The AUR) for `packaging/aur/` and its script; `ui` for those and `web.rs`, `scripts/web-dist/` and the Dockerfile; the app's checks for `app/`, `crates/` and the desktop's web parts; Android for its own parts; `slskd-contract` for the pin and the code that relies on it; `server-package` (the Linux package installed as a service on Ubuntu, Debian and Fedora and held to the hub contract, ADR-0090) for `packaging/linux/`, `tests/hub-contract/`, the pins in `app/build.rs` and the hub code only the package runs (`managed/`, `cli/`, the admin socket, kits); every other hub change reaches it in the full run on main. A change to `.github/` or `queue.sh` runs them all. Each workflow is reusable (`workflow_call` with the candidate's commit). The slow ones are split across parallel machines: `ui` six ways (the visual matrix four, Lighthouse's routes two), `ui-gates` seven (performance two, `fit` two, the rest three).
- **Everything, on main:** `main-full.yml` runs every check on main's newest commit every three hours while one has no full run, and sets its `full` status. Red files an issue. A release is cut only from a commit with both `queue` and `full` green (`scripts/release.sh`), so a check the queue skipped for a change still stands between it and listeners.
- **Green:** the candidate gets the status `queue`, main fast-forwards to it, the landed branches are deleted, and the run publishes the image `ui` tested (`:main`, `:sha-<short>`), starts Pages when `site/` changed and warms the bundles' caches when the lockfiles changed (ADR-0097). Its own pushes start no workflows, so it starts these itself.
- **Red:** the branch's tip gets `queue` = failure and the failing checks' names. A red batch of several is tried again in halves (`halve` in `queue.sh`): each tip is marked "failed in a batch of n", the next run takes the oldest half of the batch that failed last, a half that passes lands and the other half is halved in turn, and a topic that fails alone is red. One culprit among n topics is found in about log2(n) runs, and the others land on the way.
- **A run that breaks off** (a GitHub API error in `plan` or `land`) starts the next run itself while topics wait, unless the two runs before it failed too: three in a row is a fault in the queue, left to the half-hourly schedule and to whoever owns the queue.
- **GitHub's API failing for a moment** (a 5xx, or an empty answer) is asked again three times, over about 40 seconds; a refusal (4xx) is final at once. Once main has moved, nothing ends the run early: the image is still published, a topic whose `landed` status couldn't be set keeps its branch for the next run to mark "already in main", and a next run that couldn't be started is started by the run's last job.
- **One topic first:** `mise run queue:first <topic>` tests a waiting topic alone in the next run, ahead of older ones: for a fix to what every batch trips on. It marks the topic with the ref `queue-first/<topic>`, which every run reads until the topic lands, so a push's kick replacing the pending run can't lose the request (a dispatch input could).
- **Main's ruleset** requires `queue` from GitHub Actions, linear history and no force push, with no bypass: a direct push is refused unless the queue already tested that exact commit. If the queue itself is broken, the owner turns the ruleset off (Settings > Rules) to push its fix.

**Releases are batches the owner approves** (ADR-0098). The GitHub draft release "Next release" is redrawn after every landing with a `feat` or `fix` (`release-draft.yml`, `scripts/release-notes.mjs`): the proposed version, what landed since the last release by area (`scripts/release-areas.tsv` maps commit scopes to areas; an unknown scope fails it, and `ci` draws the same notes on every candidate and pull request, so that fails before landing), each area complete or waiting for its switches (ADR-0096), and the 500-character notes. A person may name the batch on its first line and edit the notes; both stay. When the owner says to release, the integrator runs `gh workflow run release.yml -f version=X.Y.Z` (or the owner runs it from the Actions tab or the GitHub app; `-f rehearse=true` tries it without pushing): it runs `scripts/release.sh` (ADR-0097: the release commit on main's newest green commit, with the draft's notes, and its tag), pushes the tag and the version commit to the queue, starts `app.yml` on the tag, and starts `release-image.yml`, which publishes the hub's image as `:X.Y.Z` and `:latest`. `release-image.yml` also runs on any `v*` tag pushed by hand, so a release made with `mise run release X.Y.Z` publishes it too. Agents never release on their own initiative. `mise run release X.Y.Z` still makes the same commit and tag locally.

**Speed.** Rust caches are saved only from main (the queue runs there) and read everywhere; the image's dependencies are a cargo-chef layer; Android's two builds run side by side.

**Android's clean build stays honest with cached dependencies.** It proves that lull's own sources give the same APK from a fresh clone in another folder, as F-Droid's build will: those sources are compiled from nothing in both builds. The third-party libraries they link come from Gradle's cache (so Maven Central's per-runner limit can't fail a build), and Gradle checks each one against the SHA-256 in `gradle/verification-metadata.xml`, so a cached library is byte for byte the one F-Droid downloads. What the check could miss is only what F-Droid's own download would differ in, and the checksums rule that out.

## Flaky checks

A check that fails without a change to blame is a bug with an owner: whoever owns its area (the table in workspace.md, or the integrator), named that day. It gets a fix at its cause, the same day. The fix's commit says what made it flaky and how the fix was proven (the same check green on runs that used to fail).

In CI, a UI test that fails runs once more on the same code (`retries` in both Playwright configs; the owner's call, 2026-11-06, so one flaky test no longer holds every landing). One that fails twice fails. One that fails and then passes is flaky: it doesn't hold the landing, and `scripts/flaky.mjs` puts a warning on the run, a line in its summary, and an open issue labelled `flaky` per test (a comment each time again) for its area's owner, who fixes the cause and closes it. Nothing else is retried, no budget is loosened, and no sleep stands in for a fix.

## Production web assets

`web/` is buildless in development and served from disk in debug builds. A release build embeds what `scripts/web-dist/build.mjs` makes of it:
- **Minified file by file, never bundled.** `index.html` loads scripts in a fixed order and designs swap `designs/<name>/design.css` by name, so every file keeps its path. CSS goes through lightningcss and JS through esbuild (both pinned in `scripts/web-dist/package-lock.json`). JS stays classic: no `format`, no `target`, so top-level names that other scripts read survive. Files already named `*.min.js` (Webamp) are left alone.
- **Pre-compressed.** Next to each text file (`.html .css .js .svg .json .webmanifest .txt .ico`) it writes `<file>.br` (brotli 11) and `<file>.gz` (gzip 9), kept only when they save 5% or more. Fonts and images are compressed already and get no variants.
- **Where it runs.** The Dockerfile's `web` stage vendors Webamp, then runs `node scripts/web-dist/build.mjs web dist`; the build stage copies `dist` over `web/`. For the app build (Tauri's `frontendDist`), `mise run web:dist [out dir]` does the same; the out dir may be `web/` itself in a throwaway CI checkout. Run the script from the repo root.

`web.rs` serves from the embedded files:
- It picks the first of `br`, `gzip` that `Accept-Encoding` allows (a `q=0` refuses it) and has a variant file, and answers with `Content-Encoding`. Without a variant, or in a checkout, it serves the plain file.
- Every answer carries `Vary: Accept-Encoding`, `Cache-Control: no-cache` and an ETag of the bytes sent, so each encoding has its own tag; `If-None-Match` gets a bodyless 304 with the same headers.
- `rust-embed` reads `web/` from disk in debug builds, so the variants don't exist there; the hub's compression layer (`compress.rs`, hub.md) then compresses those text files per request, as it does every JSON answer.

**Sizes** (`web/` at `a324215`, 144 files; the hub sent everything uncompressed before):

| | files | before (raw) | minified raw | on the wire, brotli |
|---|---|---|---|---|
| JS | 18 | 1604 KiB | 1366 KiB | 377 KiB |
| CSS | 14 | 719 KiB | 540 KiB | 96 KiB |
| everything | 144 | 3369 KiB | 2951 KiB | 1399 KiB |

The rest is the Webamp bundle, fonts, SVG and images. Brotli over the old raw transfer is the real gain: JS 1604 → 377 KiB, CSS 719 → 96 KiB.

## Visual matrix

`tests/ui/` (Playwright, pinned; `mise` is not needed, `npm ci` in that folder). `matrix.spec.mjs` makes one test per picture:
- **Routes** (`routes.mjs`): every fixed route, every Settings section, plus an album, artist, tag and playlist page found in the hub's library by `global-setup.mjs` once there is one. Add a route there when a screen registers one.
- **Designs and themes:** `lull skydeck starlight petal glasshouse` × `day night`, set through the `lull:prefs` the UI reads before first paint.
- **Viewports:** `phone` 390×844 (mobile, touch) and `desktop` 1440×900 for every route; `laptop` 1366×768, `xwide` 1920×1080 and `ultra` 2560×1440 (ADR-0007's sizes) only for the screens whose layout follows the window (`layoutRoutes` in `routes.mjs`: Home, Search, Library albums and songs, Now Playing, album, artist, playlist), so the run stays within its hour.
- **Per picture it asserts:** no horizontal overflow (names the widest element), no title squeezed under 48 px (a grid counting its columns from the window instead of its own width), no console error or uncaught exception, no failed or 4xx/5xx request, then compares the viewport screenshot (animations disabled, caret hidden, fixed clock and timezone, 0.2% of pixels tolerated).
- **Tolerated requests** are listed with their reason in `expected-failures.json`. Delete an entry when its cause lands; don't add one to get green.

**The CI hub.** `run-hub.sh` runs the built image (`lull:ui`) on host networking next to:
- `stub-slskd.mjs`: an slskd that is logged in, shares a library, answers the server's status check that every connection check makes, and gets the same one-peer, one-song answer to every search. Any call it doesn't answer would raise the Soulseek banner and shift every page under Lighthouse (2026-11-06: 0.13 on every route, once the hub began the status check), so it 404s anything else loudly and the ui job fails on those calls by name. `crates/soulseek/src/slskd.rs` changing runs the ui job for that reason.
- a fixture library (`fixtures/make-library.mjs`, ffmpeg): 4 albums, 14 tracks of 6 s sine tones, invented artists, real tags, embedded and folder covers, in `Artist/Album (Year)/NN - Title.ext`. Never commit generated media. It is mounted at `/music`.
- a dead proxy for everything outside localhost, so MusicBrainz, Cover Art Archive and the rest fail identically on every run rather than changing the pictures.
- `LULL_SETUP_CODE` and `LULL_LIBRARY=folder` are passed only once `crates/core` reads those keys (the hub refuses unknown keys), and `global-setup.mjs` claims the hub and keeps the `lull_device` cookie only once `GET /api/setup` exists (ADR-0002). Before that the hub is open.

**Goldens are not committed by the Quality session.** With no `tests/ui/goldens/`, or with `UI_CAPTURE=1`, a run writes the pictures instead of comparing, and the `ui` workflow uploads them as the `goldens` artifact. `mise run ui:update` triggers a capture run on the current branch and downloads them into `tests/ui/goldens/`; review and commit them. Pictures from any other machine differ by fonts and anti-aliasing, so only CI's image captures them. Failing runs upload `diffs` (expected, actual, diff images and the HTML report).

## Budgets

Lighthouse CI on the mobile profile (simulated slow 4G, the CPU slowed to one device), three runs per route, the median asserted. `lighthouse.sh` runs `lighthouserc.cjs` once per route in `budgets.json` (`home`, `search`, `library/albums`, `now`, `settings/playback`), because lhci drops the `#fragment` and would merge the routes into one page. Per route: the bytes lull ships (`shipped.mjs`, after each route's runs), largest contentful paint, total blocking time, cumulative layout shift.

**Shipped bytes, not the page's total.** Lighthouse's `total-byte-weight` counts every response, and the hub's live answers vary between runs of the same code: the event stream (`/api/events`, 142-392 B by how many events arrive before Lighthouse stops), `/health` read live (903-993 B), `/api/settings` and `/api/devices` by a byte or a few. That moved a route's total by up to 250 B, more than the room some budgets had, so changes that shipped nothing new failed. `shipped.mjs` counts every request but the live ones (Fetch, XHR, EventSource: 3.1-4.5 KB a route, the fixture library's state), the median of the runs: the page, scripts, styles, fonts, icons and covers, the same bytes on every run (Home 355,932 B in all three of queue run 42051194000). The budgets were moved to it at the same strictness: each kept its room over `main` (Home 107 B, search and now 452 B, library/albums 2,375 B, settings/playback 45 B). It leaves out Chrome's own fetches of the page's icons too (`app-icon.svg` and `icon-192.png`, 21,642 B, Lighthouse's type Other): the browser makes them after the page has loaded, and they race the end of the trace. When they end last, Lighthouse records them at 0 B, and settings/playback read 21,642 B less in all three runs of queue run 42108563689. Every budget went down by those 21,642 B and kept its room.

**The same device on every runner.** Lighthouse slows the CPU by a fixed factor on top of the machine it is on, and GitHub's runners differ by 2x: in a day of queue runs its benchmark of the runner (`benchmarkIndex`) went from 1,900 to 4,000, and /now's blocking time with it, 30 ms on a fast runner and 120-170 ms on a slow one for the same code, failing the 150 ms budget on slow runners only. `lighthouse.sh` measures the runner first (Lighthouse's benchmark, the median of three loads) and slows the CPU 4x times its speed over `budgets.json`'s `benchmarkIndex`, the speed the budgets are met on (3,900, `main`'s own runs before the queue: 3,555-4,013). ## Checks on a branch

The queue runs the checks on every candidate, and they run on every pull request. On any other branch, run them by hand: `gh workflow run ci --ref <branch>` (fmt, clippy, tests, the web's tests), `app` (the app's checks on Linux and Windows, then the four desktop bundles and the APK as artifacts) `ui-gates` and `share` (the share Worker's tests; on main it also deploys, share.md). Only the queue publishes the image and starts Pages; a Release comes only from a `v*` tag. A change to a workflow in `.github/workflows/` is tested by the queue with main's copy of each workflow (Actions reads a called workflow at the calling commit), so run a changed workflow on its branch by hand before it queues.

## Check in shadow

`.github/workflows/check.yml` is lull's move onto the shared CI skeleton (the `ci-skeleton` project's contract). For now it runs beside the queue and **blocks nothing**: the queue, `ship` and releases work as above and don't read it. It runs on every pull request and on every push to a `queue/**` branch (agents ship through those, so each shipped topic is checked this way too; that trigger goes when the queue does). Another workflow can call it with `all: true` to run every job. A newer push to a ref cancels its older run.

- **Jobs:** `changes` (which path-gated jobs run, from `.github/ci/paths.yml`; a job with a key there runs only when its paths changed), `check`, `privacy`, and `gate`, the one status the workflow reports (`check / gate`). `gate` fails on any failed or cancelled job and lets a job skip only when the path map left it out.
- **`check` runs `mise run check`:** fmt, clippy `-D warnings`, `cargo test`, the web's `node --test`, `scripts/release-notes.mjs draft` (a commit scope `scripts/release-areas.tsv` doesn't map fails here, not on main), `cargo update --locked` for `app/`, and the lint of the two new workflows (`actionlint` and `.github/ci/lint.py` on `check.yml` and `after.yml`; the older workflows don't meet its rules, so `mise run ci:lint` is not run). `ci.yml`'s `check` runs the same list, and `mise run check` is that list.
- **`privacy` runs `mise run privacy`:** `scripts/privacy-check.sh` over the whole history, with the `PRIVATE_PATTERNS` secret, as `privacy.yml` does.
- **The Rust cache is shared with `ci.yml`.** Both jobs are `check` on `ubuntu-24.04` and both install the pinned toolchain before `Swatinem/rust-cache`, which keys on the job id, the OS and the installed toolchains; so `check.yml` restores what `ci.yml` saves on main and never saves itself.
- **Tools** are pinned in `mise.toml` and hash-checked in `mise.lock` (Node, Python for the shared scripts, `actionlint`). Rust stays pinned by `rust-toolchain.toml`.
- **`after.yml`** reacts to a finished `check` run once it is on main: one rerun of an infrastructure failure, and an issue per flaky test. `.github/ci/` is the skeleton's code, copied unchanged; fix it in the skeleton, not here.
- **The web UI jobs** are the queue's `image`, `ui` and `ui-gates` (the paths are the queue's own, in `paths.yml`). `image` builds the hub's image once (`mise run image:save`, reading main's build cache and never writing it) and hands it on as an artifact. It has no Last.fm app key, since `check` has no secrets, so its hub has no built-in key. `ui` is the four functional shards on that image (`ui:setup`, `ui:hub`, `ui:matrix`, and on shard 1 `ui:contract`, then `ui:stub`); Lighthouse's two shards stay in `ui.yml` until `main` takes timing. `gates` is the seven behaviour-gate shards: `mise run check:ui` takes `GATES=perf|fit|rest` and `SHARD=2/3`, so a person runs one machine's share the same way.
- **Browsers** are installed by `tests/ui/setup.sh` inside those tasks. The jobs restore the `ui-browsers-...` cache that main saves (`.github/actions/ui-browsers`; same keys) and never save it.
- **Flaky UI tests** get the one retry as before. One that passes on it goes to `flakes/playwright.txt` (`mise run flakes:ui`, `scripts/playwright-flakes.mjs`), uploaded as `flakes-<job>-<slot>-ubuntu-24.04`; `after.yml` files the issue. These jobs don't call `scripts/flaky.mjs` and have no `issues: write`.

## Privacy

`.github/workflows/privacy.yml` runs `scripts/privacy-check.sh` on every push to main, and the queue can call it on what it is about to land. It fails when a commit's time zone isn't UTC, or when a file at HEAD or any commit message matches a line of the `PRIVATE_PATTERNS` secret (extended regexes, case-insensitive). The list lives only in the secret, since a list in the repository would publish what it guards. The output names files and commits, never the words. Without the secret the words check is skipped and says so. To change the list, set the secret again (`gh secret set PRIVATE_PATTERNS`).

## UI gates

`mise run check:ui` (CI: `.github/workflows/ui-gates.yml` on every change to `web/` or `tests/ui/`). Node, Chromium and WebKit only: no image, no hub, no outside service. CI runs it on seven machines at once: performance split two ways, each machine running one test at a time; `fit`, about half the rest's time, two ways; and every other gate three ways (`--shard`). `GATES` picks the projects (`perf`, `fit`, or `rest`). `GATES` in `gates/playwright.config.mjs` picks the projects for both CI and `run.sh` (`perf`, or `rest`: every other project), so a new gate runs everywhere without being listed.

**The fixture hub** (`tests/ui/fixture-hub/`): `server.mjs` serves this checkout's `web/` and answers `/api` from `library.mjs`, an invented library made by a seeded generator, the same on every run: 64 artists, 150 albums (the last ten the catalog's, unsaved; streaming one of them fails), 1,672 songs, a 1,200-song playlist (`pl-1`) and a 60-song one (`pl-2`), 300 likes, a week of history, synced lyrics. Covers are generated PNGs at the size asked (the 512 px one weighs what a photo does); audio is a silent WAV as long as the song. It models the contract in api.md, not the hub: anything it doesn't answer is a 404 the specs count as a failure, so add the endpoint there when a screen starts reading a new one. `node tests/ui/fixture-hub/server.mjs 8790` runs it by hand; `FIXTURE_TRACK_SECONDS=20` makes every song 20 s, `FIXTURE_ALBUMS=<n>` (150 or more) and `FIXTURE_LONG_PLAYLIST=<n>` make the library and `pl-1` that size (a screen's cost against a list's length), and `FIXTURE_AUDIO_DIR=<dir with song.mp3, song.flac>` serves real files (a listening soak in minutes); `LULL_WEB=<dir>` serves another `web/` (an A/B against main).

**Budgets move only with a measured reason a listener would accept** (a feature, not drift), stated in the commit with the run's numbers, as above for Lighthouse.

**Finding a cause** when a gate fails: the Chrome trace of the scenario (DevTools Performance panel, or the `summarise` numbers), and for slow style recalculation Chrome's selector stats (trace category `disabled-by-default-blink.debug`, event `SelectorStats`), which name the selector. ## Graphics

`.github/workflows/graphics.yml` runs `tests/desktop/graphics.mjs`: the real Linux app (a debug build with its own identifier) on GitHub's runner, which has no graphics card, under Xvfb, driven over WebDriver (tauri-driver and WebKitGTK's WebKitWebDriver) against the fixture hub. The queue runs it for `app/`, `web/`, `tests/desktop/` and the fixture hub, and the full run on main every time.
- **Each mode** (Automatic; Automatic with `LIBGL_ALWAYS_SOFTWARE=1`; the graphics card, started with the switches that turn it off; the processor only): the page's process (`WebKitWebProcess`, `/proc/<pid>/environ`) gets exactly the switches the mode names (docs/context/desktop.md, Graphics), the screen isn't blank, `webview.log` says what draws the page, the app finds the processor and every page takes the lighter look.
- **Never locked out:** a start in a chosen mode that ends before the listener used it comes back in Automatic with Settings' line saying why; one the listener used keeps its mode.
- **Its own hub signs in** (`tests/desktop/hub-signin.mjs`, ADR-0064): the app as its own hub, its slskd pointed at the slskd contract's stand-in Soulseek server (no real account, nothing on the real network), takes the account as Settings sends it and must say "Connected as contract-lull": once with lull's own yt-dlp, Deno and slskd, once with copies installed in `/usr/local/bin`, which it must prefer (`hub.log`'s `helpers:` line).
- **On the processor** (`tests/desktop/graphics-budget.json`), in each built-in design, in Automatic and the lighter look listeners there get: Home, Library's albums and the 1,200-song playlist are warmed, then scrolled a step every frame, and must draw at least 2 frames a second (the median of three; the listener's report was 2, unusable); and Home at rest (after the look's own repaint) must keep the page's process under 10% of a core.
