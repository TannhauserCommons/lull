# Quality: the check, web assets, visual matrix, budgets

Owned by the Quality session. Files: `scripts/web-dist/`, `crates/server/src/web.rs`, the web stage of the `Dockerfile`, `tests/ui/`, `.github/workflows/`, `.github/ci/paths.yml`, `scripts/ci/`, `ship.sh`, `merge.sh` and `release.sh`.

## Main stays green

Every change reaches main as a pull request that `check / gate` passed (Landing a change, below; ADR-0102, which supersedes the queue of ADR-0095). Main's ruleset requires `gate` from GitHub Actions, linear history and no force push. After the merge `main.yml` runs again on main the checks whose paths changed since its newest green run (all of them when it has none), and publishes the image only from a green run, and `after.yml` keeps one `main is red: <job>` issue for a check that fails there (The check: one gate, below). Two green pull requests can still break main together, since each was checked on its own head; that red shows on main's run, and the fix is a fix or a revert, revert by default.

**Releases are batches the owner approves** (ADR-0098). The GitHub draft release "Next release" is redrawn after every landing with a `feat` or `fix` (`release-draft.yml`, `scripts/release-notes.mjs`): the proposed version, what landed since the last release by area (`scripts/release-areas.tsv` maps commit scopes to areas; an unknown scope fails it, and `check` draws the same notes on every pull request, so that fails before the merge), each area complete or waiting for its switches (ADR-0096), and the 500-character notes. A person may name the batch on its first line and edit the notes; both stay. When the owner says to release, the integrator runs `gh workflow run release.yml -f version=X.Y.Z` (or the owner runs it from the Actions tab or the GitHub app; `-f rehearse=true` tries it without pushing): it runs `scripts/release.sh` (ADR-0097: the release commit on main's newest green commit, with the draft's notes, and its tag) and pushes the version commit to the branch `release-X.Y.Z`, whose pull request lands it (Landing a change). The tag publishes (`app.yml`'s installers, updater files, APK and GitHub Release; `release-image.yml`'s `:X.Y.Z` and `:latest`; F-Droid follows tags), so it goes up last, once `check / gate` passed on the version commit (ADR-0103): the run's summary gives the session the commands (open the pull request with the App's token, wait for its checks, `sh scripts/release-gate.sh <commit>`, tag, push the tag). `app.yml` and `release-image.yml` run the same `release-gate.sh` first and refuse a tag whose commit has no green `gate`. Agents never release on their own initiative. `mise run release X.Y.Z` makes the same commit and tag locally and prints the same steps.

**Speed.** Rust caches are saved only from main (`main.yml`'s `check`) and read everywhere; the image's dependencies are a cargo-chef layer; Android's two builds run side by side.

**Pinned downloads are kept, so a warm run asks no outside host.** GitHub's release host answers 5xx now and then (graphics, app, server-package and aur each went red on a 504, none on lull's code), and a retry only hides that. A file pinned by version and hash is kept with `actions/cache`, saved only from main and restored everywhere else, the way the Rust and browser caches are: `app/binaries` (the sidecars `app/build.rs` pins, key `sidecars-<OS>-<arch>-<hash of app/build.rs>`, shared by `app`, `keyring` and `graphics`); `pinned-downloads/` under the runner's temp folder, which the scripts below read as `$DOWNLOADS_CACHE`, files by hash (`scripts/ci/pinned-download.sh`; `packaging/linux/sidecars.mjs`; `tests/slskd-contract/run.mjs --native`), for the Linux package's nfpm, slskd, yt-dlp and Deno, the .NET SDK `app/slskd/build.sh` builds on, and the Windows slskd binary; the source of the release `package-secrets-update` builds from (`release-source-<hash of that script>`, which names the release; a tarball, so no `git fetch` of the tag); and aur's release files (`aur-bundles-<tag>`: the newest release is looked up every run, since that is what aur tests, but a tag already seen is not downloaded again). A kept file is used only when it hashes to the pin, and a download is kept only when it does. A pin bump changes the key, so the next main run fetches anew. Still online on purpose: aur's lookup of the newest release and makepkg's own download of the PKGBUILD's sources (which checks the PKGBUILD's URLs), the `bundle` job's release builds (tags, which must fetch fresh), `git clone` of slskd's source for its Windows build, and the first run of each key. Every `apt-get install` follows an `apt-get update` in the same step, so a runner image's stale package list can't send an install to a mirror that has moved on.

**Android's clean build stays honest with cached dependencies.** It proves that lull's own sources give the same APK from a fresh clone in another folder, as F-Droid's build will: those sources are compiled from nothing in both builds. The third-party libraries they link come from Gradle's cache (so Maven Central's per-runner limit can't fail a build), and Gradle checks each one against the SHA-256 in `gradle/verification-metadata.xml`, so a cached library is byte for byte the one F-Droid downloads. What the check could miss is only what F-Droid's own download would differ in, and the checksums rule that out.

## Flaky checks

A check that fails without a change to blame is a bug with an owner: whoever owns its area (the table in workspace.md, or the integrator), named that day. It gets a fix at its cause, the same day. The fix's commit says what made it flaky and how the fix was proven (the same check green on runs that used to fail), and ends with `Fixes #<n>` for the flaky issue it fixes; whoever ships the fix checks that the issue closed once it merged, and if not, closes it with the merged commit as proof.

In CI, a UI test that fails runs once more on the same code (`retries` in both Playwright configs; the owner's call, 2026-11-06, so one flaky test no longer holds every merge). One that fails twice fails. One that fails and then passes is flaky: it doesn't hold the merge, and `after` files one `flaky: <test>` issue per test (The check: one gate, below) for its area's owner, who fixes the cause and closes it. Besides that, `after` reruns a run once when its failure is all infrastructure (the owner's call, 2026-11-14). Nothing else is retried, no budget is loosened, and no sleep stands in for a fix.

## Production web assets

`web/` is buildless in development and served from disk in debug builds. A release build embeds what `scripts/web-dist/build.mjs` makes of it:
- **Minified file by file, never bundled.** `index.html` loads scripts in a fixed order and designs swap `designs/<name>/design.css` by name, so every file keeps its path. CSS goes through lightningcss and JS through esbuild (both pinned in `scripts/web-dist/package-lock.json`). JS stays classic: no `format`, no `target`, so top-level names that other scripts read survive. Files already named `*.min.js` (Webamp) are left alone.
- **Pre-compressed.** Next to each text file (`.html .css .js .svg .json .webmanifest .txt .ico`) it writes `<file>.br` (brotli 11) and `<file>.gz` (gzip 9), kept only when they save 5% or more. Fonts and images are compressed already and get no variants.
- **Where it runs.** The Dockerfile's `web` stage vendors Webamp, then runs `node scripts/web-dist/build.mjs web dist`; the build stage copies `dist` over `web/`. For the app build (Tauri's `frontendDist`), `mise run web:dist [out dir]` does the same; the out dir may be `web/` itself in a throwaway CI checkout. Run the script from the repo root.

`web.rs` serves from the embedded files:
- It picks the first of `br`, `gzip` that `Accept-Encoding` allows (a `q=0` refuses it) and has a variant file, and answers with `Content-Encoding`. Without a variant, or in a checkout, it serves the plain file.
- Every answer carries `Vary: Accept-Encoding`, `Cache-Control: no-cache` and an ETag of the bytes sent, so each encoding has its own tag; `If-None-Match` gets a bodyless 304 with the same headers.
- `rust-embed` reads `web/` from disk in debug builds, so the variants don't exist there; the hub's compression layer (`compress.rs`, hub.md) then compresses those text files per request, as it does every JSON answer.

**Sizes** (`web/` at `a324215`, 144 files; the hub sent everything uncompressed before):

| | files | before (raw) | minified raw | on the wire, brotli |
|---|---|---|---|---|
| JS | 18 | 1604 KiB | 1366 KiB | 377 KiB |
| CSS | 14 | 719 KiB | 540 KiB | 96 KiB |
| everything | 144 | 3369 KiB | 2951 KiB | 1399 KiB |

The rest is the Webamp bundle, fonts, SVG and images. Brotli over the old raw transfer is the real gain: JS 1604 → 377 KiB, CSS 719 → 96 KiB.

## Visual matrix

`tests/ui/` (Playwright, pinned; `mise` is not needed, `npm ci` in that folder). `matrix.spec.mjs` makes one test per picture:
- **Routes** (`routes.mjs`): every fixed route, every Settings section, plus an album, artist, tag and playlist page found in the hub's library by `global-setup.mjs` once there is one. Add a route there when a screen registers one.
- **Designs and themes:** `lull skydeck starlight petal glasshouse` × `day night`, set through the `lull:prefs` the UI reads before first paint.
- **Viewports:** `phone` 390×844 (mobile, touch) and `desktop` 1440×900 for every route; `laptop` 1366×768, `xwide` 1920×1080 and `ultra` 2560×1440 (ADR-0007's sizes) only for the screens whose layout follows the window (`layoutRoutes` in `routes.mjs`: Home, Search, Library albums and songs, Now Playing, album, artist, playlist), so the run stays within its hour.
- **Per picture it asserts:** no horizontal overflow (names the widest element), no title squeezed under 48 px (a grid counting its columns from the window instead of its own width), no console error or uncaught exception, no failed or 4xx/5xx request, then compares the viewport screenshot (animations disabled, caret hidden, fixed clock and timezone, 0.2% of pixels tolerated).
- **Tolerated requests** are listed with their reason in `expected-failures.json`. Delete an entry when its cause lands; don't add one to get green.

**The CI hub.** `run-hub.sh` runs the built image (`lull:ui`) on host networking next to:
- `stub-slskd.mjs`: an slskd that is logged in, shares a library, answers the server's status check that every connection check makes, and gets the same one-peer, one-song answer to every search. Any call it doesn't answer would raise the Soulseek banner and shift every page under Lighthouse (2026-11-06: 0.13 on every route, once the hub began the status check), so it 404s anything else loudly and the ui job fails on those calls by name. `crates/soulseek/src/slskd.rs` changing runs the ui job for that reason.
- a fixture library (`fixtures/make-library.mjs`, ffmpeg): 4 albums, 14 tracks of 6 s sine tones, invented artists, real tags, embedded and folder covers, in `Artist/Album (Year)/NN - Title.ext`. Never commit generated media. It is mounted at `/music`.
- a dead proxy for everything outside localhost, so MusicBrainz, Cover Art Archive and the rest fail identically on every run rather than changing the pictures.
- `LULL_SETUP_CODE` and `LULL_LIBRARY=folder` are passed only once `crates/core` reads those keys (the hub refuses unknown keys), and `global-setup.mjs` claims the hub and keeps the `lull_device` cookie only once `GET /api/setup` exists (ADR-0002). Before that the hub is open.

**Goldens are not committed by the Quality session.** With no `tests/ui/goldens/`, or with `UI_CAPTURE=1`, a run writes the pictures instead of comparing, and the `ui` workflow uploads them as the `goldens` artifact. `mise run ui:update` triggers a capture run on the current branch and downloads them into `tests/ui/goldens/`; review and commit them. Pictures from any other machine differ by fonts and anti-aliasing, so only CI's image captures them. Failing runs upload `diffs` (expected, actual, diff images and the HTML report).

## Budgets

Lighthouse CI on the mobile profile (simulated slow 4G, the CPU slowed to one device), three runs per route, the median asserted. `lighthouse.sh` runs `lighthouserc.cjs` once per route in `budgets.json` (`home`, `search`, `library/albums`, `now`, `settings/playback`), because lhci drops the `#fragment` and would merge the routes into one page. Per route: largest contentful paint, total blocking time, cumulative layout shift. It runs in `nightly.yml` (The check, below), not after every merge, and judges no bytes: what lull ships is the `budgets` check's, at pull request time (Budgets check, below). Its own absolute shipped-bytes budgets were raised 17 times and caught one growth that check now sees, so they went (the owner's call, 2026-11-26; ADR-0104).

**The same device on every runner.** Lighthouse slows the CPU by a fixed factor on top of the machine it is on, and GitHub's runners differ by 2x: in a day of queue runs its benchmark of the runner (`benchmarkIndex`) went from 1,900 to 4,000, and /now's blocking time with it, 30 ms on a fast runner and 120-170 ms on a slow one for the same code, failing the 150 ms budget on slow runners only. `lighthouse.sh` measures the runner first (Lighthouse's benchmark, the median of three loads) and slows the CPU 4x times its speed over `budgets.json`'s `benchmarkIndex`, the speed the budgets are met on (3,900, `main`'s own runs before the queue: 3,555-4,013). A runner at 3,900 runs at 4x as before, one at 2,000 at 2x: both play the same device, so a page's own extra work shows the same on every runner and no runner fails a page another passes.

**Measured** on the CI hub with the fixture library (run 41315307272, `main` with theme packages, minified and brotli-compressed, median of three):

| route | transfer | LCP | TBT | CLS |
|---|---|---|---|---|
| home | 369 KB | 4.3 s | 87 ms | 0 |
| search | 368 KB | 4.3 s | 40 ms | 0 |
| library/albums | 385 KB | 4.1 s | 27 ms | 0 |
| now | 367 KB | 4.0 s | 91 ms | 0 |
| settings/playback | 369 KB | 4.0 s | 52 ms | 0 |

How the baseline moved, so the next raise has a precedent to compare with:
- **302 KB, LCP 3.5 s** (run 41308967643): empty library, `main` at `a324215`.
- **326 KB, LCP 3.7 s** (run 41312904377): web changes landed on `main`; library/albums adds about 17 KB of covers.
- **369 KB, LCP 4.3 s** (this table): the themes work. A design is now a theme package: `theme.css`, `theme.json`, one HTML file per slot, `purify.min.js` (DOMPurify, 11 KB) and `/api/themes`, and `appearance.js` grew by 7 KB. LCP rose because the stylesheet, the package and its slots now load one after another. CLS fell to 0.

- **Back under the pre-themes budgets** (run 41776358581, `main` at `894d001`): the budgets were raised from the themes run while the theme stylesheet, package and slots loaded one after another, and set back to the pre-themes figures once that was fixed (83176c3, 94fa61a). Main then failed transfer by 25-28 KB and CLS on library/albums (0.078) and settings/playback (0.032) until code began loading where it is used (Classic mode and the desktop bridge 03cf1db, their stylesheets bb4f0bb, the equaliser b2e873f, one screen's code and the hub's settings c909e31) and loading screens stopped jumping when their data came (ff4ffc5); every route now passes. Covers didn't move it: library/albums' covers weighed 16 KB before and after they were sized to their box (web.md), since at Lighthouse's 412 px and 1.75x its tiles ask for 256 px either way.

**Budgets move only with a stated reason the user would accept**, never because `main` got heavier: a budget that follows every regression catches nothing. They are the pre-themes run's figures (41312904377) plus a margin:
- **LCP +25%** (3.5-3.7 s -> 4.35-4.65 s): the simulated network makes it stable, but runners differ.
- **CLS +0.025** over a median of 0 (now 0.09, set from its first measured 0.071).
- **TBT 150 ms,** not median +50%: lab TBT of 0-90 ms is noise, and a floor keeps the check from flaking while still catching a real long task.

Raise a budget only with a measured reason a listener would accept, in the commit (a feature they asked for, not drift): run the nightly, read the `lighthouse` artifact's reports, and edit `budgets.json`.

**A feature's code loads where it is used** (web.md, Code loads where it is used): a screen or panel's script and styles load on its first use, so a feature doesn't spend the start's transfer budget, and a budget isn't raised to fit code that could load on use. The on-use gate (below) fails on a new file at start that `gates/start-files.json` doesn't list with its reason. A file already at start can still grow: when the `budgets` check fails, find what in it only one screen uses and move that out (Stats left system.js this way) before reaching for the budget.

## Where the version lives

One version, held by these files (`scripts/ci/version.mjs`, tested by `tests/web/version.test.mjs`): `[workspace.package]` in `Cargo.toml` (the source), the manifest of every workspace member (each takes the workspace version or equals it; the member list is read from the two `Cargo.toml` workspaces, not named in the script; `check` and `bump` refuse a `members` or `exclude` entry they cannot resolve, such as a glob, rather than skip it), `app/Cargo.toml`, `versionCode` in `app/tauri.android.conf.json` (X*1000000 + Y*1000 + Z; minor and patch stay below 1000), and in both lock files every package lull owns: each member, `lull-app`, and the members the app reaches. A lock entry is edited by package name, never by version string: `app/Cargo.lock` has a dependency, `document-features`, that happens to share lull's number. `tauri-plugin-lull-player` has a version of its own and is not one of them.

- **`mise run version`** prints the version `Cargo.toml` carries as its last line.
- **`mise run bump X.Y.Z`** writes it into every holder, with no cargo and no network, and adds `fastlane/metadata/android/en-US/changelogs/<versionCode>.txt` (the stub `scripts/release.sh` falls back to) when there is none, staged with `git add` so that `git commit -am` carries it (in whatever git work tree lull's folder sits in, an enclosing repository included, since that is where a `git commit -am` from there commits; nothing is staged outside one). It refuses a version that is not `X.Y.Z`, one older than the current, a minor or patch of 1000 or more, a versionCode below the file's, a `Cargo.toml` version that is not `X.Y.Z`, and a read-only holder. Everything that can fail runs before a holder changes (temp files, the stub, the staging); the holders are then renamed into place and put back if one cannot be. A refusal or a failure writes nothing. Bumping to the version the tree already carries completes whatever an earlier run left undone, and does nothing on a finished tree.
- **`mise run check`** runs `node scripts/ci/version.mjs check`: it fails, naming the file, when a holder disagrees with `Cargo.toml` or a lock lacks a package it must have. `cargo ... --locked` stays the judge of the locks' structure.

`scripts/release.sh` and `release.yml` still cut releases and read the same files; they don't use these tasks yet.

## Checks on a branch

A branch's checks run on its pull request (`mise run ship <topic>`, Landing a change). Only `main.yml` publishes the image and starts Pages; a Release comes only from a `v*` tag. `ui.yml` and `ui-gates.yml` run by hand on a branch only to take new goldens (`mise run ui:update`, `mise run ui:approve`).

## The check: one gate

`.github/workflows/check.yml` is lull's move onto the shared CI skeleton (the `ci-skeleton` project's contract), and the one gate: a pull request merges when `check / gate` is green. It runs on every pull request, and `main.yml` calls it on every push to main with `base`, the commit of its newest green run, or with `all: true` when it has none (below). A newer push to a pull request cancels its older run.

- **`main.yml`** runs on every push to main, one run at a time (a newer push waits, and waiting runs collapse to the newest). It calls `check` with `base`, the commit `mise run main:plan` found as `main.yml`'s newest green run on main that is an ancestor of the push, so only the path-gated jobs whose paths changed since then run (`changes` diffs against `base`; `image` always runs, for the publish below). With no such run (the first run, a re-run of an older one, a run by hand, an API failure) `base` is empty and `check` runs every job with `all: true`; the push's own `before` is never used for this. A job that was red stays selected until a run is green, since green runs are the base. Skipped jobs are allowed by `gate` and open no `main is red` issue, as on a pull request. It passes, as secrets, `PRIVATE_PATTERNS` and Last.fm's app key and secret, so the image main builds and tests carries the key (a pull request's `check` has none: the key is read only when the event isn't a pull request). Then, each only after a green `check`: `image` publishes that image as `:main` and `:sha-<short>` (`mise run image:publish`); and these dispatch workflows on main (`mise run main:dispatch`), chosen by `mise run main:plan` from the files and commits main brought since `main.yml`'s newest green run (so a push whose waiting run a newer one replaced, or whose run was red, is planned with the next): `pages` (`site/`), `share` (the Worker's paths), `youtube-music-contract`, `release-draft` (a `feat` or `fix` came in, ADR-0098) and `warm` (`app.yml`; a lockfile or the toolchain changed, ADR-0097). Beside them runs `graphics` (`graphics.yml`, Graphics below), which needs main's quiet; a red one turns main's run red. Lighthouse runs in `nightly.yml` only.
- **`nightly.yml`** (The nightly, ADR-0104) runs once a night on main, and by hand: `check` with `all: true` and main.yml's secrets, `graphics`, and `lighthouse` (two shards of `tests/ui/lighthouse.sh` on the image `check` built; it runs only here). Its `escapes` job (`mise run nightly:escapes`, `scripts/ci/nightly-escapes.mjs`) reads main.yml's last 30 runs for each red job: one main skipped since it last ran it green is an **escape**, a path its key in `paths.yml` misses, and the issue lists the commits and files since that green run; one main ran green at its newest run is a flake or an input that is not a path; one main is red on has its `main is red` issue. It keeps one `nightly is red` issue (label `nightly-red`), closed by the next green night; `after.yml` doesn't react to it. `check`'s concurrency group holds its caller's name, so the nightly's check and main's don't cancel each other.
- **`after.yml`** (`.github/ci/after.py`, the skeleton's) reacts to every finished `check` and `main` run: it reruns a failure that is all infrastructure once, files one `flaky:` issue per flaky test from the `flakes-*` artifacts, and keeps one `main is red: <job>` issue per failed job on main, closed by that job's next green run. Fix or revert; revert by default.
- **Caches are saved by a run on main and only restored by a pull request:** Rust (`rust-cache`), the browsers' `ui-browsers-...` cache, `package-jellyfin`'s ffmpeg packages (`apt-...-jellyfin-...`), Android's cargo and Gradle downloads, mise's, and the image's layers (`image:save` writes them back when `LULL_IMAGE_CACHE_SAVE` is set).

- **Jobs:** `changes` (which path-gated jobs run, from `.github/ci/paths.yml`; each gated job has a key there, and a job added later brings its own), `check`, `privacy`, the path-gated jobs below, and `gate`, the one status the workflow reports (`check / gate`). `gate` fails on any failed or cancelled job and lets a job skip only when the path map left it out.
- **`check` runs `mise run check`:** fmt, clippy `-D warnings`, `cargo test`, the web's `node --test`, `scripts/release-notes.mjs draft` (a commit scope `scripts/release-areas.tsv` doesn't map fails here, not on main), `cargo update --locked` for `app/`, and the lint of `check.yml`, `main.yml` and `after.yml` (`actionlint` and `.github/ci/lint.py`; the older workflows don't meet its rules, so `mise run ci:lint` is not run).
- **`privacy` runs `mise run privacy`:** `scripts/privacy-check.sh` over the whole history, with the `PRIVATE_PATTERNS` secret.
- **App and contract jobs** run the app's and the contracts' checks, each as one `mise run <task>` over a script in `scripts/ci/` (POSIX sh; the Windows jobs run it with Git's sh, which the Windows runners have on PATH), so an agent runs the same task locally. Their keys in `paths.yml` hold the paths each reads, plus `.github/**` and the job's own scripts; a job that follows another (`android-compare`, the `package-*` contracts) or shares its paths (`keyring`, `slskd-windows`) has its own key with the same list, because the gate lets only a keyed job skip.

  | Job | Task | Needs |
  | --- | --- | --- |
  | `app` (Ubuntu 22.04 and Windows 2025) | `app:check`: syntax check, fmt, clippy, tests of `app/` | `app/build.rs` downloads the pinned sidecars |
  | `keyring` | `app:keyring` | GNOME Keyring, installed by the script |
  | `android` (`signed`, `clean`), `android-compare` | `android:sdk`, `android:toolchains`, `android:apk <build>`, `android:compare`, in F-Droid's build image | throwaway key, no secrets; Maven, crates.io |
  | `slskd`, `slskd-windows`, `slskd-build` | `slskd:resume`, `slskd:native`, `slskd:build` | Docker image pull; the pinned slskd zip; upstream's release |
  | `package`, `package-contract` (three distros), `package-jellyfin`, `package-self-update`, `package-secrets-update` | `package:build`, `package:contract <distro>`, `package:jellyfin`, `package:self-update`, `package:secrets-update` | Docker, distro and Jellyfin images, npm (Tauri CLI), the `v0.2.6` tag |
  | `share` | `share:test` | npm |
  | `aur` | `aur:package`, in an Arch container | pacman, the newest release's `.deb` files |

Rust caches are saved on main and restored elsewhere: rust-cache's key holds the job id, which differs from the old jobs', so each job names the old job's key with `shared-key` and hits what the old workflows saved. Nothing here uses a secret, signs or publishes; the web UI jobs are in their own section.
- **Tools** are pinned in `mise.toml` and hash-checked in `mise.lock` (Node, Python for the shared scripts, `actionlint`). Rust stays pinned by `rust-toolchain.toml`.
- **`.github/ci/`** is the skeleton's code, copied unchanged except `paths.yml`; fix it in the skeleton, not here (`after.yml` too). Its `ci:candidate` and the skeleton's `build`, `compare` and `candidate` jobs are not used: releases from candidates come later.
- **Not in `check`:** `graphics`, Lighthouse, the live YouTube Music contract and the Pages deploy. Timing and live services belong to main, so `check` leaves them out (`main.yml` and `nightly.yml` above).
- **The web UI jobs** are `image`, `ui` and `gates` (their paths in `paths.yml`). `image` builds the hub's image once (`mise run image:save`, reading main's build cache) and hands it on as an artifact; on main it is built with Last.fm's app key and then published, and a pull request's has none, so its hub has no built-in key. `ui` is the four functional shards on that image (`ui:setup`, `ui:hub`, `ui:matrix`, and on shard 1 `ui:contract`, then `ui:stub`); Lighthouse's two shards run in `nightly.yml` (`ui:lighthouse`, `LH_SHARD`). `gates` is the seven behaviour-gate shards: `mise run check:ui` takes `GATES=perf|fit|rest` and `SHARD=2/3`, so a person runs one machine's share the same way.
- **Browsers** are installed by `tests/ui/setup.sh` inside those tasks. The jobs restore the `ui-browsers-...` cache (`.github/actions/ui-browsers`; same keys), and a run on main saves it after the install.
- **Flaky UI tests** get the one retry as before. The `check` jobs have no `issues: write`.

### Budgets check

The `budgets` job (`mise run budgets`, in `check`) is the one home of **shipped bytes**; Lighthouse no longer budgets them. Which files a start loads is decided by the app's own scripts, so nothing reads the HTML or the CSS to guess: **a real browser lists the files, and their sizes come from the build.** It is path-gated (`web/`, `scripts/web-dist/`, `scripts/budgets/`, the fixture hub, Playwright's dependency files) and blocks in `check`.
- **What a start is.** Headless Chromium opens each route in `scripts/budgets/shipped-bytes.json` as a first visit, on the fixture hub (`tests/ui/fixture-hub`, the same answers every run) serving that tree's build: a fresh context per route, Lighthouse's phone (412x823 at 1.75x), light mode, the default design, no stored settings. The start is **what the page has loaded by a fixed horizon of its own time**, not by the moment a machine happens to go quiet (that moved with a busy machine and let a late load escape). Playwright's clock is installed before the page loads and paused, and time advances in 250 ms steps up to the horizon, the network allowed to finish after each step, so every timer, animation frame and idle callback due inside the horizon has run, in the same order, on every machine. The horizon is 14 s, a second short of the first load lull defers on purpose, **Classic mode, which `app.js` starts 15 s after the page is ready**: `scripts/budgets/list.mjs` reads that delay from `app.js`, so moving it moves the horizon, a delay that leaves under 10 s fails, and a Classic that loads inside the horizon fails. Outside the start: Classic, the UI sounds after a first tap or key, anything a click opens, and whatever a browser fetches on its own after load or a service worker installs. Waiting for the network waits on events, never a sleep, and only up to a real-time bound (30 s) that fails naming the requests still in flight; a request meant to stay open is recognised by what it is (an EventSource, a WebSocket, a `text/event-stream` response), never by timing. A route key must be a screen: one that matches nothing ("Nothing lives here") or redirects fails the listing, so a typo can't pass by listing the shell.
- **What is counted:** every same-origin request whose path is a file of the build (scripts, styles, fonts, images, files fetched from script), each at the bytes the hub sends for it, read from the build in `web.rs`'s order: the `.br` file, else the `.gz`, else the file. Those are **brotli sizes**, which a browser asks for only over HTTPS or localhost: a phone on a plain-HTTP LAN hub gets the gzip files, about 10% more. Response headers (about 650 B a file, the CSP most of it) and the hub's own answers (the API, covers) are not counted. The build is the tree's own `scripts/web-dist/build.mjs`, as the image's.
- **Not measured:** the service worker's install and precache (blocked), the favicon, the manifest and the touch icon (25.7 KB that a real phone fetches after load), an unpaired first visit (the pairing gate and `hub.js`), desktop width (the desk's floor and stars load from 1,100 px), a stored design or theme, and anything the fixture hub's library doesn't draw.
- **What it judges** (`scripts/budgets/decide.mjs`): the change's growth over its merge-base (`git merge-base HEAD origin/main`, or `mise run budgets <rev>`) against the **allowance** (500 B for every route unless a route names its own), in `scripts/budgets/shipped-bytes.json` with its reason and status; the allowance is a whole number of bytes with a reason, and 0 allows no growth. There is no fixed ceiling: the allowance was measured on 20 web commits (-40 to +356 B each) and those same commits added +1,169 B in two days, so a fixed ceiling a little above today's size would trip every few days and be raised each time. A route's total growth is read in the release draft against the last release. The merge-base is listed the same way, so a change that makes a route load a new file is charged for it and one that stops loading a file is credited. The merge-base's own files list, size and judge, and its limits are the ones that apply, so a change can't loosen what judges it. Three things follow the owner's own edits to the limits: when nothing grew on any route both sides measured, the change's own budgets file judges and the table says "limits changed, nothing grew" (the allowance changed, a route dropped or renamed); a route the merge-base budgets that the change's file drops is listed as removed when no screen answers to its key in the change's app any more, and fails when a screen still does; a route the merge-base doesn't know has nothing to grow from and is printed as new. A merge-base with no harness is judged by the change's own only for the change that adds the harness.
- **The check's own files are protected paths.** The entry script runs from the change's tree, and so do these inputs of the listing and the sizing, so a change to any of them can alter what judges it and is flagged to the owner in the brief, not passed by the check: `scripts/budgets/**` (the listing, sizing, judging and limits), the `budgets` job in `check.yml` and its key in `paths.yml`, the `budgets` task in `mise.toml`, `mise.lock`, `tests/ui/fixture-hub/**` (the hub the browser opens), `scripts/web-dist/**` (the build the sizes come from), `tests/ui/package.json`, `tests/ui/package-lock.json` and `tests/ui/setup.sh` (the browser), and `.github/**`. The merge-base's own copies of the harness and limits judge, apart from the owner's limit changes below.
- **When it fails** it names the route, what grew (the files and by how much) and the allowance it broke. Cut the growth first: code that one screen needs loads on its first use (web.md, Code loads where it is used). If it is still needed, attach an impact note to the change (what grew, what a listener would feel, what you tried) and wait for the owner's yes or no; a label or a commit footer never passes it. With the yes, a commit that only raises the allowance in `shipped-bytes.json`, with the owner's reason in `why`, lands first, and the change after it.
- **Locally** it needs Node and Playwright's Chromium (`mise run budgets` installs it through `tests/ui/setup.sh`); no Docker, no Rust. `node scripts/budgets/measure.mjs` prints each route's files and bytes for this tree.
- **Adding a route** is an empty entry in `shipped-bytes.json` (`"route": {}`), the same names as Lighthouse's routes in `tests/ui/budgets.json`.

## Privacy

`check.yml`'s `privacy` job runs `scripts/privacy-check.sh` (`mise run privacy`) on every pull request and on main. It fails when a commit's time zone isn't UTC, or when a file at HEAD or any commit message matches a line of the `PRIVATE_PATTERNS` secret (extended regexes, case-insensitive). The list lives only in the secret, since a list in the repository would publish what it guards. The output names files and commits, never the words. Without the secret the words check is skipped and says so. To change the list, set the secret again (`gh secret set PRIVATE_PATTERNS`).

## Landing a change

Every change reaches main as a pull request, and main's ruleset requires `check / gate` on it.

1. `mise run ship <topic>` pushes HEAD to the branch `<topic>`, opens its pull request (or updates the open one) and waits for `check / gate` on that commit. The topic says what the change holds; the repository is public.
2. It opens pull requests only with the App's token (`GH_TOKEN`): a person's account stamps its time zone on the test-merge commit GitHub makes for an open pull request. It refuses any other token.
3. Green: `mise run merge <pr>` merges it, where `home/merge-policy.toml` lets it go without the owner's yes; otherwise the owner approves it first. The merge rebases, so each commit keeps its subject for the release notes, and it names the checked head, so a push after the check makes it refuse.
4. Red: fix it on the branch and ship the same topic again.
5. After the merge, `main.yml` runs the checks whose paths changed since its newest green run on main (all, without one), publishes the image and the post-merge jobs; `after.yml` keeps one `main is red` issue for a red there (The check: one gate, above).

A release's version commit lands the same way: the release puts it on the branch `release-X.Y.Z`, and the session that ran the release opens its pull request with the App's token, since a pull request opened by a workflow's own token starts no check.
