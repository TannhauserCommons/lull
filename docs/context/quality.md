# Quality: the queue, web assets, visual matrix, budgets

Owned by the Quality session. Files: `scripts/web-dist/`, `crates/server/src/web.rs`, the web stage of the `Dockerfile`, `tests/ui/`, `.github/workflows/` and `scripts/queue.sh`, `ship.sh` and `release.sh`.

## The queue: main is always green

Main moves only through the queue (ADR-0095). `mise run ship <topic>` pushes `HEAD` to `queue/<topic>` and waits for the verdict on that commit: landed, or red with the run's link. Red leaves main untouched; fix it on your branch and ship again.

- **One run at a time** (`.github/workflows/queue.yml`, on main, started by `queue-kick.yml`): `scripts/queue.sh plan` rebases every waiting branch, oldest first, onto main and the ones before it. That stack is the candidate. A branch that doesn't rebase cleanly is set aside red ("conflicts with main").
- **Only the checks its diff needs** (`checks` in `queue.sh`): `ci` for anything but docs, `design/`, `fastlane/` and `site/`; `ui-gates` for `web/` and `tests/ui/`; `ui` for those and `web.rs`, `scripts/web-dist/` and the Dockerfile; the app's checks for `app/`, `crates/` and the desktop's web parts; Android for its own parts; `slskd-contract` for the pin and the code that relies on it. A change to `.github/` or `queue.sh` runs them all. Each workflow is reusable (`workflow_call` with the candidate's commit).
- **Green:** the candidate gets the status `queue`, main fast-forwards to it, the landed branches are deleted, and the run publishes the image `ui` tested (`:main`, `:sha-<short>`), starts Pages when `site/` changed and warms the bundles' caches when the lockfiles changed (ADR-0097). Its own pushes start no workflows, so it starts these itself.
- **Red:** the branch's tip gets `queue` = failure and the failing checks' names. A red batch of several is retried one at a time, oldest first.
- **A run that breaks off** (a GitHub API error in `plan` or `land`) starts the next run itself while topics wait, unless the two runs before it failed too: three in a row is a fault in the queue, left to the half-hourly schedule and to whoever owns the queue.
- **GitHub's API failing for a moment** (a 5xx, or an empty answer) is asked again three times, over about 40 seconds; a refusal (4xx) is final at once. Once main has moved, nothing ends the run early: the image is still published, a topic whose `landed` status couldn't be set keeps its branch for the next run to mark "already in main", and a next run that couldn't be started is started by the run's last job.
- **One topic first:** `gh workflow run queue.yml -f first=<topic>` tests that topic alone in the next run, ahead of older ones: for a fix to what every batch trips on.
- **Main's ruleset** requires `queue` from GitHub Actions, linear history and no force push, with no bypass: a direct push is refused unless the queue already tested that exact commit. If the queue itself is broken, the owner turns the ruleset off (Settings > Rules) to push its fix.

**Releases are batches the owner approves** (ADR-0098). The GitHub draft release "Next release" is redrawn after every landing with a `feat` or `fix` (`release-draft.yml`, `scripts/release-notes.mjs`): the proposed version, what landed since the last release by area (`scripts/release-areas.tsv` maps commit scopes to areas; an unknown scope fails it), each area complete or waiting for its switches (ADR-0096), and the 500-character notes. A person may name the batch on its first line and edit the notes; both stay. When the owner says to release, the integrator runs `gh workflow run release.yml -f version=X.Y.Z` (or the owner runs it from the Actions tab or the GitHub app; `-f rehearse=true` tries it without pushing): it runs `scripts/release.sh` (ADR-0097: the release commit on main's newest green commit, with the draft's notes, and its tag), pushes the tag and the version commit to the queue, starts `app.yml` on the tag, and publishes the hub's image as `:X.Y.Z` and `:latest`. Agents never release on their own initiative. `mise run release X.Y.Z` still makes the same commit and tag locally.

**Speed.** Rust caches are saved only from main (the queue runs there) and read everywhere; the image's dependencies are a cargo-chef layer; Android's two builds run side by side.

**Android's clean build stays honest with cached dependencies.** It proves that lull's own sources give the same APK from a fresh clone in another folder, as F-Droid's build will: those sources are compiled from nothing in both builds. The third-party libraries they link come from Gradle's cache (so Maven Central's per-runner limit can't fail a build), and Gradle checks each one against the SHA-256 in `gradle/verification-metadata.xml`, so a cached library is byte for byte the one F-Droid downloads. What the check could miss is only what F-Droid's own download would differ in, and the checksums rule that out.

## Flaky checks

A check that fails without a change to blame is a bug with an owner: whoever owns its area (the table in workspace.md, or the integrator), named that day. It gets a fix at its cause, the same day. It never gets a retry, a re-run until green, a sleep, or a loosened budget, and it stays required while it is fixed: a check that can't be trusted can't guard main. The fix's commit says what made it flaky and how the fix was proven (the same check green on runs that used to fail).

## Production web assets

`web/` is buildless in development and served from disk in debug builds. A release build embeds what `scripts/web-dist/build.mjs` makes of it:
- **Minified file by file, never bundled.** `index.html` loads scripts in a fixed order and designs swap `designs/<name>/design.css` by name, so every file keeps its path. CSS goes through lightningcss and JS through esbuild (both pinned in `scripts/web-dist/package-lock.json`). JS stays classic: no `format`, no `target`, so top-level names that other scripts read survive. Files already named `*.min.js` (Webamp) are left alone.
- **Pre-compressed.** Next to each text file (`.html .css .js .svg .json .webmanifest .txt .ico`) it writes `<file>.br` (brotli 11) and `<file>.gz` (gzip 9), kept only when they save 5% or more. Fonts and images are compressed already and get no variants.
- **Where it runs.** The Dockerfile's `web` stage vendors Webamp, then runs `node scripts/web-dist/build.mjs web dist`; the build stage copies `dist` over `web/`. For the app build (Tauri's `frontendDist`), `mise run web:dist [out dir]` does the same; the out dir may be `web/` itself in a throwaway CI checkout. Run the script from the repo root.

`web.rs` serves from the embedded files:
- It picks the first of `br`, `gzip` that `Accept-Encoding` allows (a `q=0` refuses it) and has a variant file, and answers with `Content-Encoding`. Without a variant, or in a checkout, it serves the plain file.
- Every answer carries `Vary: Accept-Encoding`, `Cache-Control: no-cache` and an ETag of the bytes sent, so each encoding has its own tag; `If-None-Match` gets a bodyless 304 with the same headers.
- `rust-embed` reads `web/` from disk in debug builds, so the variants don't exist there; the hub's compression layer (`compress.rs`, hub.md) then compresses those text files per request, as it does every JSON answer.

**Sizes** (`web/` at `a324215`, 144 files; the hub sent everything uncompressed before):

| | files | before (raw) | minified raw | on the wire, brotli |
|---|---|---|---|---|
| JS | 18 | 1604 KiB | 1366 KiB | 377 KiB |
| CSS | 14 | 719 KiB | 540 KiB | 96 KiB |
| everything | 144 | 3369 KiB | 2951 KiB | 1399 KiB |

The rest is the Webamp bundle, fonts, SVG and images. Brotli over the old raw transfer is the real gain: JS 1604 → 377 KiB, CSS 719 → 96 KiB.

## Visual matrix

`tests/ui/` (Playwright, pinned; `mise` is not needed, `npm ci` in that folder). `matrix.spec.mjs` makes one test per picture:
- **Routes** (`routes.mjs`): every fixed route, every Settings section, plus an album, artist, tag and playlist page found in the hub's library by `global-setup.mjs` once there is one. Add a route there when a screen registers one.
- **Designs and themes:** `lull skydeck starlight petal glasshouse` × `day night`, set through the `lull:prefs` the UI reads before first paint.
- **Viewports:** `phone` 390×844 (mobile, touch) and `desktop` 1440×900 for every route; `laptop` 1366×768, `xwide` 1920×1080 and `ultra` 2560×1440 (ADR-0007's sizes) only for the screens whose layout follows the window (`layoutRoutes` in `routes.mjs`: Home, Search, Library albums and songs, Now Playing, album, artist, playlist), so the run stays within its hour.
- **Per picture it asserts:** no horizontal overflow (names the widest element), no title squeezed under 48 px (a grid counting its columns from the window instead of its own width), no console error or uncaught exception, no failed or 4xx/5xx request, then compares the viewport screenshot (animations disabled, caret hidden, fixed clock and timezone, 0.2% of pixels tolerated).
- **Tolerated requests** are listed with their reason in `expected-failures.json`. Delete an entry when its cause lands; don't add one to get green.

**The CI hub.** `run-hub.sh` runs the built image (`lull:ui`) on host networking next to:
- `stub-slskd.mjs`: an slskd that is logged in, shares a library and gets the same one-peer, one-song answer to every search. Unanswered searches are how lull spots a wedged slskd, so a stub that found nothing would raise the Soulseek banner after a few searches and shift every page under Lighthouse. It answers only what `crates/soulseek/src/slskd.rs` calls and 404s anything else loudly.
- a fixture library (`fixtures/make-library.mjs`, ffmpeg): 4 albums, 14 tracks of 6 s sine tones, invented artists, real tags, embedded and folder covers, in `Artist/Album (Year)/NN - Title.ext`. Never commit generated media. It is mounted at `/music`.
- a dead proxy for everything outside localhost, so MusicBrainz, Cover Art Archive and the rest fail identically on every run rather than changing the pictures.
- `LULL_SETUP_CODE` and `LULL_LIBRARY=folder` are passed only once `crates/core` reads those keys (the hub refuses unknown keys), and `global-setup.mjs` claims the hub and keeps the `lull_device` cookie only once `GET /api/setup` exists (ADR-0002). Before that the hub is open.

**Goldens are not committed by the Quality session.** With no `tests/ui/goldens/`, or with `UI_CAPTURE=1`, a run writes the pictures instead of comparing, and the `ui` workflow uploads them as the `goldens` artifact. `mise run ui:update` triggers a capture run on the current branch and downloads them into `tests/ui/goldens/`; review and commit them. Pictures from any other machine differ by fonts and anti-aliasing, so only CI's image captures them. Failing runs upload `diffs` (expected, actual, diff images and the HTML report).

## Budgets

Lighthouse CI on the mobile profile (simulated slow 4G, the CPU slowed to one device), three runs per route, the median asserted. `lighthouse.sh` runs `lighthouserc.cjs` once per route in `budgets.json` (`home`, `search`, `library/albums`, `now`, `settings/playback`), because lhci drops the `#fragment` and would merge the routes into one page. Per route: the bytes lull ships (`shipped.mjs`, after each route's runs), largest contentful paint, total blocking time, cumulative layout shift.

**Shipped bytes, not the page's total.** Lighthouse's `total-byte-weight` counts every response, and the hub's live answers vary between runs of the same code: the event stream (`/api/events`, 142-392 B by how many events arrive before Lighthouse stops), `/health` read live (903-993 B), `/api/settings` and `/api/devices` by a byte or a few. That moved a route's total by up to 250 B, more than the room some budgets had, so changes that shipped nothing new failed. `shipped.mjs` counts every request but the live ones (Fetch, XHR, EventSource: 3.1-4.5 KB a route, the fixture library's state), the median of the runs: the page, scripts, styles, fonts, icons and covers, the same bytes on every run (Home 355,932 B in all three of queue run 42051194000). The budgets were moved to it at the same strictness: each kept its room over `main` (Home 107 B, search and now 452 B, library/albums 2,375 B, settings/playback 45 B).

**The same device on every runner.** Lighthouse slows the CPU by a fixed factor on top of the machine it is on, and GitHub's runners differ by 2x: in a day of queue runs its benchmark of the runner (`benchmarkIndex`) went from 1,900 to 4,000, and /now's blocking time with it, 30 ms on a fast runner and 120-170 ms on a slow one for the same code, failing the 150 ms budget on slow runners only. `lighthouse.sh` measures the runner first (Lighthouse's benchmark, the median of three loads) and slows the CPU 4x times its speed over `budgets.json`'s `benchmarkIndex`, the speed the budgets are met on (3,900, `main`'s own runs before the queue: 3,555-4,013). A runner at 3,900 runs at 4x as before, one at 2,000 at 2x: both play the same device, so a page's own extra work shows the same on every runner and no runner fails a page another passes.

**Budgets move only with a stated reason the user would accept**, never because `main` got heavier: a budget that follows every regression catches nothing. They are the pre-themes run's figures (41312904377) plus a margin:
- **Transfer +10%** (358-360 KB, library/albums 377 KB), then **+1.5 KB** for lull's candy desktop (the default design's stylesheet loads at start: 18,991 B to 20,326 B shipped, brotli; queue run 41959608736 measured each route 0.5-1.3 KB over): a redesign the listener asked for, not drift. settings/playback **+400 B** more for the sound checks' three YouTube rows (the AcoustID key, Contribute to AcoustID, the AcoustID user key, ADR-0016): the key's field alone measured 9 B over (queue run 41995620995), and the owner asked for the rows. settings/playback **+300 B** more for lull's buttons by role, every key on the candy desktop in its gel (the default design's stylesheet: 20,340 B to 20,536 B shipped, brotli): queue run 42019373736 measured that route 134 B over, nothing in the stylesheet could go without changing the look, and the owner asked for the change. It moves only when we change files (shipped bytes, above), so the margin is small. A change that adds a script or a font fails it.
- **LCP +25%** (3.5-3.7 s -> 4.35-4.65 s): the simulated network makes it stable, but runners differ.
- **CLS +0.025** over a median of 0 (now 0.09, set from its first measured 0.071).
- **TBT 150 ms,** not median +50%: lab TBT of 0-90 ms is noise, and a floor keeps the check from flaking while still catching a real long task.

Raise a budget only with a measured reason a listener would accept, in the commit (a feature they asked for, not drift): run the workflow, read the `lighthouse` artifact's reports, and edit `budgets.json` the same way.

**A feature's code loads where it is used** (web.md, Code loads where it is used): a screen or panel's script and styles load on its first use, so a feature doesn't spend the start's transfer budget, and a budget isn't raised to fit code that could load on use. The on-use gate (below) fails on a new file at start that `gates/start-files.json` doesn't list with its reason. A file already at start can still grow: when Lighthouse's transfer goes over, find what in it only one screen uses and move that out (Stats left system.js this way) before reaching for the budget.

## Checks on a branch

The queue runs the checks on every candidate, and they run on every pull request. On any other branch, run them by hand: `gh workflow run ci --ref <branch>` (fmt, clippy, tests, the web's tests), `app` (the app's checks on Linux and Windows, then the four desktop bundles and the APK as artifacts) `ui-gates` and `share` (the share Worker's tests; on main it also deploys, share.md). Only the queue publishes the image and starts Pages; a Release comes only from a `v*` tag. A change to a workflow in `.github/workflows/` is tested by the queue with main's copy of each workflow (Actions reads a called workflow at the calling commit), so run a changed workflow on its branch by hand before it queues.

## Privacy

`.github/workflows/privacy.yml` runs `scripts/privacy-check.sh` on every push to main, and the queue can call it on what it is about to land. It fails when a commit's time zone isn't UTC, or when a file at HEAD or any commit message matches a line of the `PRIVATE_PATTERNS` secret (extended regexes, case-insensitive). The list lives only in the secret, since a list in the repository would publish what it guards. The output names files and commits, never the words. Without the secret the words check is skipped and says so. To change the list, set the secret again (`gh secret set PRIVATE_PATTERNS`).

## UI gates

`mise run check:ui` (CI: `.github/workflows/ui-gates.yml` on every change to `web/` or `tests/ui/`). Node, Chromium and WebKit only: no image, no hub, no outside service. CI runs it on four machines at once (about eight minutes): performance alone on one, every other gate split three ways (`--shard`). `GATES` in `gates/playwright.config.mjs` picks the projects for both CI and `run.sh` (`perf`, or `rest`: every other project), so a new gate runs everywhere without being listed.

**The fixture hub** (`tests/ui/fixture-hub/`): `server.mjs` serves this checkout's `web/` and answers `/api` from `library.mjs`, an invented library made by a seeded generator, the same on every run: 64 artists, 150 albums (the last ten the catalog's, unsaved; streaming one of them fails), 1,672 songs, a 1,200-song playlist (`pl-1`) and a 60-song one (`pl-2`), 300 likes, a week of history, synced lyrics. Covers are generated PNGs at the size asked (the 512 px one weighs what a photo does); audio is a silent WAV as long as the song. It models the contract in api.md, not the hub: anything it doesn't answer is a 404 the specs count as a failure, so add the endpoint there when a screen starts reading a new one. `node tests/ui/fixture-hub/server.mjs 8790` runs it by hand; `FIXTURE_TRACK_SECONDS=20` makes every song 20 s, `FIXTURE_ALBUMS=<n>` (150 or more) and `FIXTURE_LONG_PLAYLIST=<n>` make the library and `pl-1` that size (a screen's cost against a list's length), and `FIXTURE_AUDIO_DIR=<dir with song.mp3, song.flac>` serves real files (a listening soak in minutes); `LULL_WEB=<dir>` serves another `web/` (an A/B against main).

**Performance** (`gates/perf.spec.mjs`, budgets in `gates/perf-budgets.json`, scenarios in `gates/scenarios.mjs`). The CPU is slowed 4x and each scenario is read from a Chrome trace: counts that don't move between runs (elements restyled, layouts, main-thread frames, bytes) wherever possible, and task lengths with about twice the measured time as room for a slower runner. Per design (all five): one class flip, text change or insertion restyles at most a hundred elements on Home, a playlist and Now Playing; the hover highlight is complete in the first frame, and a sweep over the long playlist causes no layout (but a tooltip opening) and spends under 100 ms in event handlers (the bug that made the highlight trail spent 320); at rest, with a song loaded and paused and the desktop app's bridge stubbed in (Home, the long playlist, Now Playing; day and night), no main-thread frames, and the design's loops drawn cheaply (themes.md, Drawing cheaply): every loop on screen changes at most 30 times a second (stepped where it is declared), moves only by transform and opacity, and stays clear of live glass, and the compositor draws at most 44 frames in 2 s (`idleDrawnFrames`: the fastest loop at rest changes 20 times a second, where an unpaced one drew a frame per refresh and kept the GPU process busy while lull sat paused) and keeps no more composited layers than the design's budget, in windows of area, each layer counted up to one window (`compositedWindows`, measured plus about 0.4: a window-sized layer more, such as a fixed sky, fails); playing costs under 220 ms a second on Now Playing (about 60 measured), its loops held to the same rules. In lull: "Pause animations when lull isn't the active window" is off by default, and on, holds the decorative loops (no frames drawn) while the window has no focus, keeps a spinner going and lets go with focus back; startup, scrolling (and the elements left on the 1,200-song playlist: under 5,000, only rows near the screen have contents), a long list against a short one (the 1,200- and 5,000-song playlists, each on a fixture hub of its own with the same library, opened and scrolled top to bottom, then measured after a garbage collection: the same elements besides the empty rows, one DOM node and no picture more a song, and at most 8 KB of the renderer's whole private footprint more a song opened, 35 KB scrolled through; measured 3.5-5.5 and 11-23, with only the rows near the screen drawn 16 and 75, before that 98) and moving between screens, typing a search, opening a menu, dragging in the queue, resizing the panel, playing beside a 1,200-song list, and a compressed listening session (60 songs skipped through, in a playlist of mixed albums, while the screens change, the desktop app's bridge stubbed by `gates/desktop-bridge.js`): heap, nodes and listeners left behind, and what crosses to the mini player (a snapshot under 2 KB, the cover once per song).

**Loops in every engine** (`gates/loops.spec.mjs`, projects `loops` and `loops-webkit`): in every design and theme, on Home and on Now Playing with a song playing, in Chromium and in WebKit (WebKitGTK on CI's Linux, the engine of lull's Linux app and of Safari), every loop that never ends changes at most 30 times a second, read from its timing (`steps(n)`, or a stepped easing's flat stretches: `loopRate` in lib.mjs), a new one included; with `App.still` asked, every decorative loop is paused and only lull's progress parts (spinners, loading sheens, transfer edges) keep going; after, all move again. perf.spec counts the frames in Chromium's trace; this checks the property where there is no trace. `node scripts/loop-easings.mjs --check web` (in `mise run check:ui`) keeps every stepped easing exact.

**Every theme, at a glance** (`tests/ui/themes-check.mjs`, `mise run themes:check -- <route>...`, local only): the routes given, with a song in the player, on desktop and phone, day and night, in the five designs and each package in `LULL_THEMES_DIR` (copied first, so nothing is written to it), on the fixture hub. Each picture gets `checks.mjs`'s `chrome`, `overflow`, `unclippedClamps` and `squeezed`, and its console errors; one contact sheet shows them all, with what was found under each, and it exits 1 when something was. For a quick look at a UI change, not a gate: the gates are the full matrix.

**Loops a theme makes costly** (`gates/theme-loops.spec.mjs`, project `theme-loops`): Theme Studio names a falling-petals loop with no rate, its Add it writes 20, and the preview's loop is then stepped to 20 and held when asked, as the loops gate measures; it names a glow that animates `box-shadow`, one inside glass, and a speck its previews see pass under glass (and not once it is moved clear); importing such themes offers the rate, or says what it can't tell; and Studio, started from each of the five designs, finds nothing on Home or Now Playing. `tests/web/loops.test.mjs` checks the detector (`web/designs/loops.js`: a loop has its rate when it is stepped and held where it is declared, or names one) and that the built-in designs and the docs' examples give it nothing to say.

**Key screens** (`gates/screens.spec.mjs`): Home, a search, a playlist, an album, Now Playing and Settings, in every design and theme, at a phone (390x844), a laptop (1366x768) and a wide window (1920x1080). Each must load without console errors or failed requests, keep inside the window, give every title room, keep the tags side by side one height on one centre line with one icon size (`checks.mjs` `unevenTags`: the source badge, quality chip and "new" mark in rows, album headers and the device facts), clip whatever it clamps to some lines (`unclippedClamps`), show every cover whole in the rows and lists that scroll it (`clippedCovers`: a ring or outline a design draws round a cover, cut by a shelf, which clips at its padding box because it scrolls; along the shelf only where its content starts or ends), and match its golden in `gates/goldens/linux/`. Goldens are CI's only (fonts and anti-aliasing differ elsewhere); on another system a first run writes its own, gitignored, so later runs compare against them. **Approving a change in how a screen looks:** push, then `mise run ui:approve` (it runs the workflow in capture mode and downloads the pictures), review `git diff --stat tests/ui/gates/goldens` and the pictures, and commit them with the change. A failing run uploads `gates-diffs-<part>` from each machine that failed (expected, actual and diff images).

**Covers** (`gates/covers.spec.mjs`, web.md "Covers at the size they are drawn"): counts the fixture hub keeps (`/__fixture/art-requests`, so the browser's cache hits don't count), each test in its own scope there (its context sends `X-Fixture-Client`): the gates beside it on the hub never add to its counts, see its covers pending or get its `art.ready`. On Home, the 1,200-song playlist and an album: every cover on screen loaded within 2 s of the page settling, no cover URL asked for twice, and no more cover requests than cover images in the page. A cover the hub is still fetching (`/__fixture/art-pending`: 404 "not yet", `no-store`) is asked once per size and not again for 6 s; `art.ready` (`/__fixture/art-ready`) makes the page ask once more and show it. At 1x and 2x, every cover asks for the smallest served size that covers its box in device pixels (10% slack), never past the 512 px the fixture's pictures have (it serves the hub's five sizes, capped there, with `X-Image-Size`). Against `web/` before this work it fails the retry and the 2x sizes. The screen sets the hub's order (ADR-0033): on a fixture hub of its own with the 5,000-song playlist and every cover cold (`/__fixture/art-cold`: the hub gets one every 100 ms, in the order of the client's latest `PUT /api/pictures/screen`, visible then near, then covers asked that no screen shows), a fast scroll to two thirds down must have the covers on the screen it stops on be the next ones the hub gets (within as many turns plus 4), and shown by then; against `web/` before this work the scrolled-past rows' covers come first. An artist drawn without a photo is reported at size 0 (`/__fixture/screen`), and the photo `art.ready` then brings in `images` shows on every cover of the artist, with no page read again.

**The chrome at every width** (`gates/fit.spec.mjs`, the check is `chrome` in `checks.mjs`): in every design and theme, with a song loaded, the window is narrowed from 2560 to 360 px and widened back, 20 px at a time, and at each step, as the frame that first draws the width shows it (checked inside that frame, by a resize observer made after the page's own, once the fitter has fitted it and before it is painted: a row a frame late fails, and a width no frame has drawn yet is never judged), the header, the player bar, the mini player and the tab bar must keep every control inside its bar and the window, never put one control on another, never cut text without an ellipsis, and keep play, previous, next, the player's "…" and search. At each width Home's rows must also show every cover whole (`clippedCovers`, as on the key screens): a shelf of round windows whose rims were drawn outside the cover lost them along the row's edge. The desktop app's mini player is checked at its own sizes (the device 340 px wide, the strip 540 x 90). The header and the bar fit themselves (web.md, Rows that fit themselves), so a failure here means a part needs a place in the give-way order, not a width band. Text that grows in place (wider letter-spacing on the header and the bar, as a label that grew; no row resizes) and fonts that arrive (a narrow one, a wider one, the narrow one again) must leave the rows within two frames as a fresh fit of everything would, at 1440, 1140 and 960 px, and what gave way comes back when the narrow font does. A width that fails says what the rows looked like then (each part's box and whether it gave way, the fonts' state), how often the page's resize observers ran, what threw and what else changed in the header and the bar since the step began, and whether the next frame and the settled page still overflow.

**Code loaded on use** (`gates/on-use.spec.mjs`, web.md "Code loads where it is used"): code that belongs to one screen or panel loads on its first use. A browser must start with exactly the scripts and stylesheets `gates/start-files.json` lists, each with the reason the start needs it: a new one fails until it loads on use (the documented way: a route's `need`, `App.needScript`) or is listed with its reason; one listed but gone fails too, so the list stays true. What loads on use must still work as before, each pinned: a .wsz dropped anywhere becomes the Classic skin, Classic opens styled and leaving it returns to the page it was opened from; Stats shows styled on its first visit; Settings > Appearance shows Classic's group; Settings > Library, Sources and Devices open on the first click with hub.css; first-run setup opens with its steps; an unpaired device lands on the pairing gate with only its placeholder before the form; a `library.source` event before hub.js loads fetches the library source and setup reads again and shows in Settings > Library once it opens; the Connect picker is styled without hub.css. In the desktop app (the bridge stubbed in) Classic and the bridge load with the page and a crash report from Webamp's window reaches classic.js without Classic having been opened. Each check fails with its part taken out.

**Long lists** (`gates/lists.spec.mjs`, web.md "Long lists cost what short ones do"): on the 1,200-song playlist, on a fixture hub of its own (it likes, downloads and reorders), what a listener does works on every row, drawn or not, and a row drawn again shows its own song: every row has its name and a place in the tab order, the arrow keys reach a row forty down drawn and on screen, and a focused row keeps its contents far away; Shift-click selects across rows never drawn; a song 800 rows down moves to the top by native drag, its row kept while dragged out of view; the queue's pointer drag moves a song 600 rows down; "playing from" opens the playlist at a song 900 rows down, lit, drawn, focused and fully in sight, where it stays while the rows around it are drawn, in every design on a laptop and a phone (and on a laptop every empty row holds a drawn row's height); a like and a download made while a row is away show when it is drawn, and so does undoing them; after jumps up and down the list no row on screen is blank and every drawn row's title, like, source, download mark, bars and cover are its own song's; on a phone, touch swipes leave no blank row on screen.

**Now Playing in every design** (`gates/now.spec.mjs`): with a song playing and its lyrics asked for in the side panel, Now Playing at a phone, a laptop, a short (1440x700) and a wide window, and the Now column, must show the title, artist, album, quality and "playing from", and the lyrics in one place only (web.md, One place shows the lyrics). Pages from different designs can then be mixed. With a long title ("Part III-Sampson & Shane-Fisher's Legend-The Big Idea") and the source details shut and open, nothing on Now Playing overlaps: no two panels (beyond the edge two joined windows share), no two lines of the heading, not the title's words and the action buttons, and no clamped line drawn past its clamp.

**Running the gates beside another checkout:** the fixture hub listens on 8790 and a local run reuses a hub already there, which may serve another checkout's `web/`. Give yours its own port: `FIXTURE_PORT=8797 mise run check:ui`.

**Accessibility** (`gates/a11y.spec.mjs`): axe-core, WCAG 2.2 A and AA, on the same screens in every design and theme. `gates/a11y-known.json` lists the violations main had when the gate arrived, each with its rule and where; a new one fails. The list only shrinks: fix one, delete its entry.

**Budgets move only with a measured reason a listener would accept** (a feature, not drift), stated in the commit with the run's numbers, as above for Lighthouse.

**Finding a cause** when a gate fails: the Chrome trace of the scenario (DevTools Performance panel, or the `summarise` numbers), and for slow style recalculation Chrome's selector stats (trace category `disabled-by-default-blink.debug`, event `SelectorStats`), which name the selector. The pattern behind most of the fixes so far: a `:has()` on a page-wide element whose argument can be anywhere walks the whole page each time it is checked; limit it to where the element sits (`.main:has(> :where(.view) > .now)`; `:where()` keeps the specificity) or use a state lull already sets (docs/themes.md, Staying fast).


## Theme hooks

`tests/web/theme-hooks.test.mjs` (part of `mise run check`) keeps docs/themes.md section 11, the hook reference, complete. It fails when:
- a class block lull's CSS or a built-in design styles is listed neither as stable nor as internal;
- a `data-*` attribute web/ sets or styles is listed in neither;
- a built-in design styles a class or attribute web/ no longer has, so the rule never matches;
- the reference lists a hook web/ no longer has, or lists one as both.

A new hook is added to section 11 in the same commit: as stable when a theme may style it, else as internal.
